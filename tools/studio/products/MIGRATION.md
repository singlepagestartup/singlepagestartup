# Products: модели и перенос Business

Изменение применяется к основному фреймворку и к дочернему слою `startup`.
Начальный этап `00-business` сохраняется: Brief → первоначальные Product,
модели и Sales → продуктовый Research → Strategy. Номер `40 Products` обозначает
место материалов в Studio, а не момент первого описания модели.

## Карта страниц

| Страница                       | Задача читателя и место редактирования                                                                                                                                                                                                                               | Аспекты модели                                                                   |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Brief                          | Запрос, полномочия, цели, исходные ограничения, перечень продуктов                                                                                                                                                                                                   | Исходный контекст                                                                |
| Product                        | Понять продукт целиком: название, категория, состояние, владелец, границы; роли клиентов, обстоятельства, задачи/проблемы/выгоды; альтернативы, ценность, состав, исключения, единица результата, использование, поддержка, права, приёмка, доказательства и решения | Customer Segments, Value Propositions                                            |
| Operations & Economics         | Понять обеспечение и экономику модели: общая область действия, условия оплаты по продуктам, ресурсы, действия, партнёры, затраты и финансирование                                                                                                                    | Revenue Streams, Key Resources, Key Activities, Key Partnerships, Cost Structure |
| Sales                          | Прочитать весь процесс клиента: ответственные, входы/данные, действия, переходы/передачи, отказы, ошибки, незавершённые действия, сопровождение, удержание, метрики                                                                                                  | Channels, Customer Relationships; операционные Key Activities                    |
| Promotion                      | Открыть из одного списка Website, Marketing Creative или Presentation; каждый материал сохраняет собственный источник, страницы, Text/Layout и экспорт                                                                                                               | Практическое применение утверждённых фактов                                      |
| Product Content, необязательно | Уроки, выпуски, документы, шаблоны и другие материалы самого продукта                                                                                                                                                                                                | Предоставляемая ценность                                                         |
| Analytics                      | Собрать текущие наблюдаемые значения воронки, использования, удержания, выручки и затрат с периодами, источниками и ограничениями                                                                                                                                    | Обратная связь по проверяемым аспектам                                           |
| Research                       | Интерпретировать конкретные наблюдения и другие источники: вопрос, метод, ограничения, противоречия и следствия для решения                                                                                                                                          | Любые проверяемые аспекты                                                        |

В боковой папке `40 Products` находятся соседние группы `singlepage` и `startup`,
а внутри — только продукты соответствующего слоя. Пустой слой показывает
`No products`; отдельной ветки default и выбора слоя под каждым продуктом нет.
Группы автоматически строятся из каталогов; ссылки используют слой и устойчивый
ID продукта. Вычисляемый default сохраняет наследование и полную замену каталога. На странице остаётся
навигация по документам, без дополнительного меню блоков канвы. Покрытие девяти
блоков описано в карте выше. Отдельного повторяющего обзора/канвы нет. Sales и Research остаются связными
материалами. Для основных документов используется ориентир около 1 400 слов без жёсткого лимита; дополнительные страницы
могут иметь собственную структуру и прежние форматы.

## Структура

```yaml
schema: singlepagestartup.product-catalog.v2
models:
  - id: learning-service
    name: Learning service
    source: models/learning-service/model.md
products:
  - id: course
    model: learning-service
    name: Course
    summary: A bounded learning offer.
    product: course/product.md
    research: course/research.md
    analytics: course/analytics.md
    sales: course/sales.yaml
    # Website/Creative/Presentation добавляются на этапе подготовки материалов.
  - id: coaching
    model: learning-service
    name: Coaching
    summary: Guided application of the course.
    product: coaching/product.md
    research: coaching/research.md
    analytics: coaching/analytics.md
    sales: coaching/sales.yaml
```

Модель хранится один раз в `products/<layer>/models/<id>/model.md`. Другую модель
объявляют отдельным ID; один продукт не требует автоматически отдельной канвы.
При общей команде/ресурсе нескольких моделей можно указать `uses: [other-model]`
и сослаться на ресурс его владельца. Циклы и отсутствующие ID запрещены.
Платёжные условия помечены ID продукта; общий расход считается один раз, либо
распределяется по явно заданному основанию. Финансирование не смешивается с
выручкой клиентов.

Пустой startup-каталог наследует весь singlepage, включая модели. Первый продукт
в startup заменяет весь каталог вместе с моделями. Нельзя ссылаться на модель
из другого слоя или восстанавливать отдельный отсутствующий файл из singlepage.
Существующие `sections/pages/children`, Markdown, HTML, JSX/TSX, изображения,
аудио, видео, дополнительные React PDF-страницы, `content`, `video` и
`website_component` сохраняются. Старые `content`/`video` показываются как Product
Content; пользовательские имена дополнительных вкладок не переписываются.

## Таблица переноса

| Старый источник/поле                              | Новый владелец                                  | Что сохранить и как убрать дубль                                                                  |
| ------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Business: продукты, пользователи, ценность        | Brief — перечень; Product — полное предложение  | ID, границы, все роли, задачи/проблемы/выгоды, альтернативы; удалить повторные описания сегмента  |
| Business: цена, доход, механика оплаты            | Model Revenue Streams                           | Условия отдельно по продуктам; Sales ссылается на них, исполняя процесс                           |
| Business: финансирование                          | Model Funding                                   | Источник денег, условия, ограничения; отдельно от клиентской выручки                              |
| Business: ресурсы, команда, партнёры, затраты     | Model Delivery and resources / Cost Structure   | Ответственность, общая область действия, лимиты, источники и основание распределения              |
| Business: конкретный процесс/передача             | Sales либо существующий цельный процесс         | Все этапы и исключения; не распределять процесс по блокам канвы                                   |
| Business: запрос, цели, полномочия                | Brief                                           | Только проектный контекст, без подробного пересказа моделей                                       |
| Business: обещания, ограничения, права, результат | Product                                         | Поддержка, лицензия, приёмка, существенные зависимости, доказательства                            |
| Business: источники/материалы                     | Рядом с утверждением; Research/Assets по смыслу | ID, атрибуция, даты наблюдений, ограничения; без нового общего реестра                            |
| Product Overview                                  | Product                                         | Все шесть тем; Best-fit customer → Customer Segments, Positioning and value → Value Propositions  |
| Исторические метрики и результаты                 | Analytics                                       | Значения, период, знаменатель, источник и ограничение; определения остаются в Product/Sales/model |
| Research                                          | Research внутри Analytics                       | Весь ход исследования, источники, противоречия; добавить ID модели и проверяемого предположения   |
| Website/Creative/Presentation                     | Исходные файлы внутри Promotion                 | Содержание и расширения сохраняются; группировка меняет навигацию, а не владельца                 |
| Подтверждения и зависимости Business              | Фактические новые владельцы и stale потребители | Сохранить атрибуцию, не переносить старое подтверждение на новое тело; не подставлять свежие хеши |

## Порядок миграции дочернего проекта

1. До изменения сохраните рабочее состояние обычным Git-процессом. Определите
   активный слой по конфигурации. В дочернем проекте редактируйте только startup;
   источники singlepage служат контекстом, не доказанными фактами клиента.
2. Выполните read-only диагностику:

   ```sh
   bun tools/studio/products/migrate.ts --layer startup
   ```

   Она перечисляет продукты без модели и разделы старого Business. V1 остаётся
   читаемым во время разбора; Studio показывает необходимость атрибуции модели.

3. Составьте таблицу переноса для **фактического содержания** проекта. Проверьте
   каждую строку и вложенный материал. Решите границы моделей, принадлежность
   общих ресурсов, условия отдельных продуктов и распределение расходов.
   Автоматически эти решения не выводятся из количества продуктов.
4. Создайте модельные источники по `product-model.md`; добавьте `models` и ссылки
   `model` в существующий каталог. Перенесите уникальные утверждения с источниками,
   обозначая неизвестные сведения. Sales переносите целиком. Не удаляйте продукт
   из-за неготовности или отсутствия в эксперименте. Добавьте `analytics.md` по
   шаблону. Если измерений нет, зафиксируйте `not measured`, а не нулевые значения.
5. После атрибуции доступна механическая часть:

   ```sh
   bun tools/studio/products/migrate.ts --layer startup --apply-structure
   ```

   Она проверяет наличие назначенных моделей, переводит каталог на v2 и меняет
   три старых заголовка Product. Сохраняет YAML-комментарии, поля, страницы,
   уникальные тексты, confirmation и старые dependency-хеши. Она **не переносит
   смысл автоматически, не удаляет Business и не подтверждает содержание**.

   После синхронизации общих файлов обычный запус
   `singlepagestartup` сам выполняет pipeline compatibility reconciliation.
   Он вернёт к `40-products` старый непустой startup-каталог без
   `analytics.md`, создаст новый источник в startup-слое и отметит
   отсутствующие измерения как `not measured`. Группировка
   Product/Promotion/Analytics приходит из общего renderer и не
   требует копирования UI в дочерний проект.

6. Вручную/агентом после содержательной проверки: удалите оставшиеся дубли,
   перенесите уникальные расширения в предусмотренные страницы, обновите ссылки,
   индексы/`uses`/правила GitHub-reconciliation на настоящих владельцев. Удалите
   старые dependency-ключи Business и добавьте `review.stale` с новыми владельцами;
   оставьте новые входы без просмотренных хешей до реальной проверки.
7. Сверьте таблицу переноса, затем удалите Business-файлы, его story и локальные
   шаблоны/индексы. Не оставляйте скрытый Business как второй источник.
   Общие файлы фреймворка уже обновлены. Историю сохраняет Git.
8. Старый курсор `[business]` замените на `[product-models]` в `00-business`.
   Поздний проект возвращается только к самому раннему незавершённому владельцу;
   отсутствие подтверждённых модели/условий не означает завершённую миграцию.
   Следующая обычная команда pre-development сверяет текущие источники и критерии.
9. Проверки:

   ```sh
   bun tools/studio/workspace/validate.ts --active-layer startup --self-check
   npm run studio:presentation:test
   npm run studio:validate
   npm run studio:storybook:build
   bun tools/studio/workspace/document-review.ts --file apps/studio/workspace/products/startup/models/learning-service/model.md
   ```

   В Studio проверьте оба слоя/default, свой каталог, цельность Product/Sales,
   вложенные страницы, Product → Overview/Product Content,
   Promotion → Website/Creative/Presentation, Analytics → Analytics/Research,
   Presentation → Prepare PDF и старые адреса.
   Измените тестовую копию общей модели: все потребители должны стать stale,
   без обновления собственного текста или подтверждения. Верните тестовую правку.

Прежние Storybook-адреса `workspace-00-business-03-business--<projection>`
(и старые `workspace-business`/`workspace-00-client-request-02-business` варианты)
переходят в `workspace-40-products-<layer>--product-<product-id>` с запросом страницы модели.
Прежний общий адрес `workspace-40-products--<projection>` также переводится
на выбранный через `product` либо первый продукт нужного слоя, сохраняя раздел и режим экспорта.
Адреса прошлой группировки `workspace-40-products-<product-id>--<projection>`
тоже поддержаны. Для default слой выбирается по правилу атомарного каталога;
отсутствующий запрошенный продукт открывает сообщение об отсутствии, без подмены другим.
Прямой `iframe.html?id=...` поддержан. Старые ссылки на Markdown-файл в других
документах нужно заменить по таблице владельцев: один универсальный редирект
для разнесённых по смыслу фактов был бы неоднозначным.

Старые query-адреса `section=content`, `section=website`,
`section=creative`, `section=presentation` и `section=research` остаются
рабочими. Studio переводит их соответственно в
`section=product&surface=content`, `section=promotion&surface=...` или
`section=analytics&surface=research`.

## Содержательная приёмка

Для каждой страницы проверьте: тема читается целиком; редактируемое утверждение
имеет одного владельца; все исходные поля/материалы сохранены; применимые блоки
раскрыты и связаны; нет пустых страниц ради метода; понятно, какой источник
редактировать. Отдельно проверьте первичную гипотезу, факт клиента и внешнее
наблюдение: подтверждение пользователя не превращает гипотезу в рыночное
доказательство.

Основа: [Business Model Generation](https://www.strategyzer.com/library/business-model-generation),
[Business Model Canvas](https://www.strategyzer.com/library/the-business-model-canvas),
[девять блоков](https://www.strategyzer.com/business-models-the-toolkit-to-design-a-disruptive-company),
[Value Proposition Canvas](https://www.strategyzer.com/library/the-value-proposition-canvas).
Группировка страниц — решение фреймворка, а не предписание авторов метода.
