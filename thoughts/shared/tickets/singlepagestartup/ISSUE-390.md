## Задача

Администратору проекта нужно выдать роли право на действие с условием: читать свой заказ, читать сообщения чата при участии в нём или создавать сообщение в доступном чате. Разработчику дочернего проекта нужен способ настроить такое правило для своего маршрута без правки ядра RBAC и копирования проверки в каждый обработчик.

Сейчас Permission определяет маршрут и HTTP-метод. У связи `RolesToPermissions` уже есть текстовое поле `condition`, но при авторизации Subject извлекает из связей только идентификаторы ролей. В #346 сервис Permission знает путь Social для чтения чатов, а обработчик сообщений отдельно проверяет связь профиля с чатом. ## Вопросы проектирования

1. Сравнить JSON-правила на Role и условия на конкретной связи `Role → Permission`. Показать обе модели на примере одной роли с разными условиями для чата и заказа. Описать, как администратор сохраняет правило, какие ошибки видит при проверке формата и как настройки переносятся через штатные dump и seed.
2. Описать контракт одного сервиса авторизации. На входе — подтверждённый Subject, действие, совпавший Permission и именованные параметры маршрута. На выходе — решение о доступе. Показать, как ID или slug однозначно разрешается в объект и как по данным сервера проверяются владелец, автор или участие. Для создания проверяется доступ к родительскому объекту, поскольку новой записи ещё нет. Подстановка чужого ID в URL или автора в теле запроса не должна давать права.
3. Предложить небольшой набор проверяемых условий JSON и точку расширения в `startup`. Общий сервис применяет правила, владеющий модуль предоставляет проверку нужной связи. Условия не должны исполнять произвольный код или SQL. Определить поведение при нескольких ролях, пустом и некорректном условии, отсутствии объекта и недоступности проверки. Ошибка проверки не должна открывать доступ.
4. Описать переход для существующих проектов. Учесть публичные Permissions без роли, точный публичный Permission демочата, административные права и существующие значения `condition`. Указать, когда можно убрать конкретную проверку из обработчика или исключение из `isSensitiveRoute`. Для списка и `count` показать, как ограничивается сама выборка. Для кэша определить, как отзыв роли или выход из чата прекращает доступ.

## Как принять проект

- Приведены примеры JSON и таблица ожидаемых решений для гостя, владельца, участника, постороннего и администратора. Среди примеров — свой и чужой заказ, приватный и явно опубликованный чат, создание сообщения, подмена профиля или родительского объекта.
- На действующем маршруте `/api/rbac/subjects/:id/social-module/profiles/:socialModuleProfileId/chats/:socialModuleChatId/messages` отдельно разобраны GET и POST. Показано, какие данные нужны для каждого решения, откуда они читаются и что изменится после исключения участника из чата.
- Приведён пример подключения ресурса дочернего проекта и сценарии проверки на свежей и существующей БД. Результат этой задачи — архитектурное предложение для согласования перед реализацией.

Связанные работы: #303 и #346 — маршруты без роли, #347 и #352 — проверки владельца в операциях с заказами.
