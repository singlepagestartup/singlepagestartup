## Зафиксированные решения

1. **Публичный author handle — Profile UUID.** Маршрут `/authors/[social.profiles.id]`; Social SDK `authorFindById({id})`. DTO не содержит private Profile.slug, Subject/Identity IDs, adminTitle, allowedMcpServerIds, Chats/Threads/Knowledge. Миграция slug, новый CAS endpoint и изменение старых Profile slugs не нужны. Новый personal Profile сохраняет совместимую серверную генерацию private slug, но public URL от slug не зависит.
2. **Eligibility публичного автора:** только поддерживаемые human/editorial варианты default/telegram и явная Profile→Article либо Profile→Product связь. Editorial Profile без RBAC owner допустим. Пустой новый аккаунт не появляется в каталоге до публикации. Public projects — явные Product links; private AI workspace aggregate не используется.
3. **Account и authoring используют реальную authenticationMe.** Guest JWT сохраняет свои account/cart/paid-entitlement права, но без Identity не получает Article-create. `authenticated`, а не cookie/JWT shape, определяет account menu. Настройки — существующий `/ai-chat/settings`; Chats — `/ai-chat/projects`; sign-in — существующий singular `/rbac/subject/authentication/select-method`. Все ссылки локализуются штатным способом.
4. **My author page** показывается только после успешного public `authorFind({profileId})`. До этого доступны settings и Create article. Новый пользователь не получает ссылку на 404. Успешная первая публикация обновляет author queries и делает публичный Profile ID доступным в меню.
5. **Article creation — одна команда владельца.** Subject SDK `blogModuleArticleCreate({id,data:{requestId,title,subtitle?,description,categoryId?}})`; POST `/api/rbac/subjects/:id/blog-module/articles`. Нужны matching JWT, Identity и human Subject. Title и body обязательны; codeBlock — необязательная часть rich text. Сервер выбирает personal Profile и defaults. Profile/owner/relation/variant/slug/id из payload запрещены. Валидированный UUID requestId даёт серверный уникальный slug `article-${requestId}`; Article.id генерируется обычным repository. Generic insert, который удаляет data.id, не меняется.
6. **Повтор создания:** тот же Subject, requestId, нормализованный payload и точные owner/author links возвращают ту же Article. Изменённый payload, чужой slug/request collision или неполный чужой граф дают 409 без деталей записи. Article + Subject→Article + Profile→Article + необязательная Category→Article создаются в одной настоящей транзакции прямыми owning Services, без loopback HTTP. Публичная модель Article не имеет draft status: форма явно сообщает о публикации.
7. **Новые статьи видны в общем Blog feed.** Главный Widget получает явный `article-feed-default` с обычным Article find/count и стабильной пагинацией; Popular остаётся curated. Пустая curation не превращается неявно во все записи. Первый successful create проверяется в public feed и на author page, а не только по прямому URL.
8. **Credits:** initial Free +3000 один раз после подтверждённой регистрации/authentication; каждый принятый оплаченный Pro cycle +5000; top-up = quantity × pack credits. Балансы additive и nonexpiring. Expiry/cancel/revoke меняют Role/access/renewal, но не обнуляют wallet или другие Currencies. Новые allowance buckets и изменение существующего AI admission threshold не входят в работу.
9. **Free eligibility** зависит от собственного initial-Free history/claim. Неоплаченная Pro cart, другой active subscription и истёкший Free не заменяют это правило. Новый Subject получает не более одного успешного initial grant при concurrency; partial Free checkout продолжается с теми же сохранёнными IDs. Free не возобновляется автоматически и не доступен для повторной self-service покупки.
10. **Catalog retirement** исключает старые примеры из явной публичной selection, не удаляя исторические Product/Order/Invoice/Role/Store records. Внутренний `free-subscription` сохраняет ID/slug и bootstrap references. Pro сохраняет ID и private Article/Role associations. Publication tool не вызывает proceed и не начисляет credits.

## Граница коммерческого применения

Подтверждены: Free initial 3000, Pro 5000 credits, Landing USD 100, Startup from USD 2000. Принятый engineering scope реализует эти правила на typed fixtures и текущих сохранённых данных, отделяя commercial application в R2.5b. Новую цену/период Pro и точные pack prices/credits/rounding разрешено применять только из отдельного подтверждённого оператором input manifest. Эти значения не выводятся из test minute/RUB/Star records или старого Studio retail-rate текста. До такого input R2.5b имеет статус pending и не меняет эти attrs/pack memberships; независимые backend/UI, Landing/Startup и остальные data changes выполняются. Финальный отчёт явно сообщает этот pending scope, не объявляя commercial application завершённым.

## Фаза R2.1: серверные границы account, authoring и public authors

**Owner:** account/backend агент по таблице; root — общая DI/API integration и policy publication. Ревью делает другой агент.

**Где/что:**

При existing personal link не искать замену по slug; поддержать default/telegram, исключить AI/foreign/ambiguous links. Прямой effective Profile create joins ambient transaction; не создавать второй Profile после изменения private slug.
- Subject controller/middleware/service/SDK: authenticated-only create, один автор от сервера, транзакция и durable requestId slug. Operation DTO размещается среди существующих Subject SDK/model command schemas. Сервер принимает locale maps только с ключами EN/RU: хотя бы одна locale содержит непустые title и body, каждый переданный title/body имеет соответствующую пару. Subtitle необязателен. Пустые locale entries нормализуются одинаково при create/retry; request locale не выводится из cookie. UI требует title, summary и body в текущей locale, вторую позволяет пропустить; codeBlock опционален. Лимиты: total payload 256KiB, title 160 chars/locale, subtitle 500 visible chars, body 100k chars/locale, TipTap depth 20/nodes 5000; разрешённые nodes/marks/code и safe links, без HTML/unsupported metadata. Транзакция проверяет exact Subject/author/category associations; ошибка link insert откатывает весь Article.
- Social Profile service/SDK/model DTO: `authorFind({params:{profileId?,blogModuleArticleId?,ecommerceModuleProductId?,limit?,offset?}}): Promise<IAuthorSummary[]>`, `authorFindCount({params:{profileId?,blogModuleArticleId?,ecommerceModuleProductId?}}): Promise<number>` и `authorFindById({id}): Promise<IAuthorDetail | null>`. SDK request/result DTO, отдельные query keys и exact public read permissions обязательны для всех трёх операций; fallback на private generic Profile.count запрещён. Только allowlisted public summaries/details, approved avatar data, Article/Product refs. Запросы используют owning Services и общий consistency capture; arbitrary generic Profile filters не принимаются. Public avatar DTO: File ID, path/URL, MIME/extension/alt/width/height, без внутренних admin fields.

Создание первого Article, удаление последней публичной связи, изменение Profile/avatar и пустой author query корректно инвалидируют list/detail/byline/feed. Private Chat сохраняет уже существующий authorized participant map из `includeParticipants=true`; scoped Message/Action DTO дополняются allowlisted sender/actor display+avatar только для Message/Action доказанно доступного Chat. Это обслуживает и ушедших участников, не имеющих public Article. `MessageProfileLoader`, `ActionProfileLoader`, `chat-profile-avatar` принимают эти данные и не открывают generic Profile для fallback.

Effective Services связывает apps/api, Social→RBAC imports не добавлять. Собственные Profile читаются через уже существующий Subject scope; MCP/operator и настоящий admin продолжают работать.

Исправить Subject README: collection — exact owner, POST — AI-only.

## Фаза R2.2: token fulfillment и once-only Free

**Owner:** fulfillment агент по таблице; root последовательно интегрирует запрошенные DI/repository/facade changes.

**Где/что:** `billing/free-subscription.ts`, Telegram free helper, `ecommerce/order/proceed.ts`, owning order/subject repository transaction capabilities и существующие billing/balance helpers.

- **Free transport и транзакция:** заменить Free bootstrap checkout/activate отдельной internal direct-Service операцией в существующем `billing/free-subscription` service. Она не вызывает SDK Product.checkout, Order.checkout, dummy provider, Order.check/proceed HTTP, Observer pipeline или polling. Обычный paid checkout сохраняет свой транспорт. Под Subject lock и ambient `withConsistencyDatabase` перечитать human Identity, eligibility, точный `free-subscription` Product и принадлежащие Subject Free Orders. До записи проверить saved zero Price+Currency, валидный interval, sole/default Store и Topup 3000. Через effective owning Services создать или продолжить Order `type=history/status=paid`, Subject→Order, один Free Product quantity 1, Store→Order, Order→Currency, PaymentIntent `amount=0/status=succeeded/type=one_off`, Order→PaymentIntent, PaymentIntent→Currency, Invoice `amount=0/status=paid/provider=dummy` и PaymentIntent→Invoice. `one_off` внутреннего PaymentIntent исключает recurring provider contract; тип/период Product и accepted Order period сохраняются. Чужие, неоднозначные, corrupt или nonzero graph histories отвергаются.
- Settlement — trusted server-only запись нулевых Invoice/Intent через их owning Services в той же transaction; public body/provider/webhook не подтверждает её. Минимально расширить typed direct-service capabilities `create` для Billing Intent/Invoice/Intent→Currency/Intent→Invoice и Ecommerce Order→Intent, сохранив shared transaction context. Нет нового claim table, queue или общей переработки checkout. Subject оркестрирует Free; Billing не импортирует RBAC/Ecommerce.
- **Общие locks и fulfillment:** eligibility, создание/repair графа, zero settlement, fixed-period Invoice acceptance, Role grant, balance +3000 и итоговый delivering/history status находятся в одной database transaction. Lock order для Free и обычного fulfillment: existing `rbac.order-delivery.subject:${subjectId}` advisory key, затем `rbac.order-delivery.order:${orderId}` и owning Order lifecycle row lock. Для нового Order его ID получают под Subject lock, затем берут Order locks; existing partial Order выбирают и перечитывают под тем же Subject lock. Выделить transaction-aware paid-fulfillment core из `fromPaidStatus`/`applyPaidStatus`: internal Free вызывает его в текущей transaction, ordinary entry открывает transaction один раз. Не держать transaction открытой через loopback HTTP и не открывать второй connection/lock scope для вложенного delivery. Telegram использует тот же internal Free путь после своего Identity bootstrap, без отдельного Telegram checkout/invoice transport.
- Fulfillment возвращает effect descriptors; mutation effects сохраняются существующим transactional consistency механизмом, notifications/revalidation и другие transport effects запускаются после outer commit. Free не регистрирует checkout Observer pipeline. Отказ post-commit notification не переигрывает credit. Удалить Free activate polling и ожидание двух checkouts из concurrency test. Ошибка до commit откатывает graph/settlement/grant/balance целиком; retry после неизвестного ответа на committed transaction читает accepted anchor и возвращает уже обработанный результат. Trusted initial Free начисляет ровно 3000 без существующего invited-Profile bonus; paid referral rewards вне этого Free path сохраняются.
- Subject-scoped cart/checkout команды запрещают прямое повторное приобретение внутреннего Free Product по его ID/slug. Только trusted authentication bootstrap может выполнить initial/resume Free operation; доверие задаётся серверной orchestration, не body flag, provider строкой или browser headers. Скрытие карточки не считается этим запретом. Operator maintenance не отменяет once-rule при fulfillment.
- Разделить fulfilled Free history, resumable pending Free и unrelated Pro cart. Server-owned accepted period/invoice anchor — durable marker новых Free grants, меняется атомарно с balance/status. Для legacy истории delivery/terminal status означает подарок уже обработан и не переигрывается при нулевом wallet; canceled/ambiguous legacy records fail closed без нового gift. Единственный oldest owned `new`/`paying`/`paid` Free Order без accepted marker можно продолжить после проверки его actual zero-price Invoice; existing related IDs сохраняются. Два старых pending/paid Free Orders не дают два credit grants: fulfillment повторно проверяет общий once-rule под тем же Subject lock. Не восстанавливать предположительно потерянные исторические balances массовым повтором оплаты.
- Удалить blanket balance zero и в canceling394–419, и в delivered976–1005. Free исключить из automatic renewal. Сохранить проверку price0, ownership, current Role/period/revocation, неизменяемые paid Invoice anchors и failed AI deduction reversal.
- `collectTopupCurrencies` учитывает quantity, суммирует реальные numeric Topup attributes по Currency и проверяет finite positive inputs. Убрать Product-global suppression, который поглощает новый paid Pro Order при другом delivering Pro.
- Initial Pro delivery, другой оплаченный Pro Order и `renewSubscription` начисляют +5000 ровно один раз на свой accepted paid Invoice/Order transition. Period anchor и credit update атомарны; OPEN/unpaid/replayed/older/revoked Invoice не дают credits. One-off packs dedupe по fulfilled paid Order, а не Product за всю жизнь пользователя.

**Real DB proof Free:** в maintained PostgreSQL integration создать disposable registered Subject и real zero-price Product/Store/Currency graph; запретить весь network transport. Параллельные direct authentication-Free operations дают один Order/Intent/Invoice и +3000; отдельный delivery job на старый duplicate pending Order не добавляет credits. Инъецировать отказ после Order link, после paid settlement и после conditional balance update: после rollback отсутствуют частичный graph, paid Invoice/grant и balance delta; повтор заканчивает один корректный grant. Потерянный ответ после commit и Telegram/common login retry возвращаются к тому же accepted Order без нового credit. Проверить общий lock order с concurrent ordinary paid delivery, а не только mock callback.

**Автоматическое принятие:** параллельные authentication/login/Telegram начисляют 3000 один раз; partial resume, unknown response и retry не создают второй gift; новая неоплаченная Pro cart не подавляет Free. Прямой guest/registered Free cart/quick-checkout request и forged bootstrap flag не создают второй grant. Free expiry/no renewal и Pro expiry/cancel/revoke сохраняют Token и остальные balances. Первый paid Pro начисляет 5000, retry — 0, второй paid Order — ещё 5000, same-Order paid renewal — 5000 один раз; unpaid/canceled/revoked Invoice — 0; quantity 2 удваивает pack credits. Обязательны actual local PostgreSQL transaction и fixed-period tests; external payments/notifications не вызываются. Top-up-only owner с достаточным balance сохраняет AI route, но не private Blog entitlement.
