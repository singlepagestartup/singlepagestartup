# Host Revalidation Secret Implementation Plan

## Overview

The host's `GET /api/revalidate` answers only callers that present
`HOST_SERVICE_REVALIDATION_SECRET` in the `X-HOST-REVALIDATION-SECRET` header,
compared in constant time. The three API-side callers send it and encode their
query values, and local bootstrap and the deployer carry one value to both
services.

## Current State Analysis

Research: `thoughts/shared/research/singlepagestartup/ISSUE-315.md`.

- The route revalidates any tag or path for any caller
  (`apps/host/app/api/revalidate/route.ts:7-32`); nothing runs in front of it
  (`apps/host/middleware.ts:24-28`). Repeating `?path=/&type=layout` empties the
  host's page and data caches, which otherwise hold for a day
  (`apps/host/app/[[...url]]/page.tsx:10`).
- Three API-side callers exist: the revalidation middleware
  (`libs/middlewares/src/lib/revalidation/index.ts:126-132`, unencoded tag, no
  header, status ignored), the API seed on every container start
  (`apps/api/src/db/seed.ts:409-417`, sends `X-RBAC-SECRET-KEY`, which the host
  never reads), and the agent page cache
  (`libs/modules/agent/models/agent/backend/app/api/src/lib/controller/singlepage/page/cache.ts:69-85`,
  unencoded path, no header). No live browser caller exists.
- A secret shared by two services is wired like
  `MCP_SERVICE_INTERNAL_TOKEN_EXCHANGE_SECRET`: generated by
  `apps/api/create_env.sh`, copied by the sibling `create_env.sh`, and
  operator-supplied in deployment through `.env.example`, the service scripts,
  the templates and both GitHub secret lists.

## Desired End State

- A request to `/api/revalidate` without the header, with a wrong value, or to
  a host that has no value configured gets `401 {"error":"Unauthorized"}` and
  revalidates nothing. The three refusals look the same to the caller.
- A host with no value configured writes a warning naming the variable on
  every call; a wrong or missing credential on a configured host is refused
  without a log line.
- A request with the configured value behaves as today for `tag`, `path` and
  `type`.
- The middleware, the seed and the agent page cache send the header; the
  middleware and the agent page cache encode their query values; the
  middleware logs a warning with the status when the host refuses.
- The API's boot report names `HOST_SERVICE_REVALIDATION_SECRET` when it is
  missing or short, without stopping the process.
- `./up.sh` on a fresh checkout writes one generated value into
  `apps/api/.env` and the same value into `apps/host/.env.local`.
- The deployer carries an operator-supplied value to both services, and the
  deployer README documents generation, rotation and the upgrade step.

Verification: the new and extended specs, a mutation check of each guard,
lint and type checks, template rendering with dummy values, and the API on
port 4315 calling a stub host that records the request.

### Key Discoveries:

- The host cannot import `@sps/backend-utils` (its barrel carries the Bun
  WebSocket manager, a pino logger and hono helpers, and no runtime host file
  imports it), and `@sps/shared-utils` stays free of node built-ins because
  client components import it (`libs/shared/utils/src/lib/secret-strength/index.ts:66-71`).
  The comparison therefore lives in the route file, as the MCP app keeps its
  own `secretsAreEqual` (`apps/mcp/lib/oauth.ts:1080-1087`).
- `rbacSecretMatches` is bound to `RBAC_SECRET_KEY` and cannot compare a
  second secret (`libs/shared/backend/utils/src/lib/rbac-secret/index.ts:23-36`).
- The operator-secret middleware answers one 401 for every rejection
  (`libs/middlewares/src/lib/operator-secret/index.ts:8-13`).
- `jest.setup.ts` loads `apps/api/.env` and `apps/host/.env.local` into every
  test process, so specs mock the secret rather than read it.
- The deployer README states the deployer generates no secret
  (`tools/deployer/README.md:126-141`); a Jinja template cannot call
  `generate_secret`, and `api.sh` and `host.sh` run separately.
- The root `create_env.sh` runs the host's script before the API's
  (`create_env.sh:50-55`), so the host could not copy a value the API has not
  generated yet.

## What We're NOT Doing

- No value generated inside the deployer. Each service script would generate
  its own value and the two services would disagree. New deployments receive
  the placeholder from `tools/deployer/.env.example`, like every other
  deployment secret, and the README tells the operator to generate it.
- No fail-open mode for a host without a value. The route stays closed and
  says why in the host log on every call, and the API boot report names the
  missing value. The trade-off: a deployment or checkout that upgrades
  without setting the value keeps serving cached pages for up to the one-day
  page window after an edit, until the operator sets one value on both
  services. No use case needs an unauthenticated caller, so no switch is added.
- The route keeps its method, query parameters and response for authorized
  calls; no CORS change (browsers cannot send the custom header cross-origin).
- The unmounted admin-v2 settings action stays as it is. A browser cannot hold
  the secret, so mounting it later needs an operator-authenticated API route
  that calls the host.
- The `/api/revalidation/revalidate` calls in `apps/host/app/global-error.tsx`
  and `apps/host/src/db/seed.ts` stay; they reach no handler today.
- The agent page cache keeps sending a full page URL as `path`; only its
  encoding changes.
- Other host routes are outside this ticket; SEC-25 in the 2026-09-25 review
  names only the revalidation route.
- `TELEGRAM_SERVICE_WEBHOOK_SECRET` stays missing from
  `tools/deployer/github_deployer.sh`; that gap predates this issue.

## Implementation Approach

Name and place the contract once in `@sps/shared-utils` (the variable in the
host envs file, the header name in the shared constants), guard the route
with a fail-closed constant-time check, then update each sender and the
environment carriers. Framework behavior stays in the shared files; no
startup seam is needed because a project configures the value, not code.

## Phase 1: Shared contract and host guard

### Overview

The route refuses every call without the configured secret.

### Changes Required:

#### 1. Shared contract

**File**: `libs/shared/utils/src/lib/envs/host.ts`
**Why**: environment values are read through the envs files; host values live here beside `HOST_SERVICE_URL`.
**Changes**: add `HOST_SERVICE_REVALIDATION_SECRET` with no default and a comment that an absent value refuses every call.

**File**: `libs/shared/utils/src/lib/constants/index.ts`
**Why**: the header name is a literal shared by the host route and three API callers.
**Changes**: add `HOST_SERVICE_REVALIDATION_SECRET_HEADER = "X-HOST-REVALIDATION-SECRET"` with a JSDoc naming the issue.

#### 2. Host route

**File**: `apps/host/app/api/revalidate/route.ts`
**Why**: the handler itself decides access; no middleware runs for `/api`.
**Changes**: before reading the query, refuse with 401 when the variable is unset (warning to the host log naming the variable, never a value) or when the header does not match; compare in constant time in a private function beside the handler (length check, then `timingSafeEqual` from `node:crypto`). Everything after the guard stays as it is.

#### 3. Host route spec

**File**: `apps/host/app/api/revalidate/route.spec.ts` (new)
**Why**: regression test for the finding and the callers' use cases.
**Changes**: BDD suite calling `GET` with a `NextRequest`; `next/cache` and the secret mocked. Scenarios: no header, same-length wrong value, different-length value, unconfigured host (warning, no revalidation), configured value with a tag carrying reserved characters (decoded exactly, no second parameter), configured value with `path=/&type=layout` (the seed's call), configured value with `type=page` (the agent's call).

## Phase 2: API senders and boot report

### Overview

Every API-side caller authenticates and encodes; a refused call is visible.

### Changes Required:

#### 1. Revalidation middleware

**File**: `libs/middlewares/src/lib/revalidation/index.ts`
**Why**: the per-mutation caller named by the finding.
**Changes**: `revalidateTag` encodes the tag with `encodeURIComponent`, sends the header, and logs a warning through the shared logger with the status when the host answers non-OK; the existing network-error branch logs through the same logger.

**File**: `libs/middlewares/src/lib/revalidation/index.spec.ts`
**Changes**: extend the suite header; scenarios for the credential and the encoded tag (the parsed URL carries exactly one `tag`), both payloads of a successful mutation through `init()`, a refused call logged without the secret, and an unreachable host logged without throwing.

#### 2. API seed

**File**: `apps/api/src/db/seed.ts`
**Why**: runs on every API container start and revalidates the root layout.
**Changes**: the host request sends the revalidation header instead of `X-RBAC-SECRET-KEY`, so the operator secret no longer travels to the host; the log label names the real path.

#### 3. Agent page cache

**File**: `libs/modules/agent/models/agent/backend/app/api/src/lib/controller/singlepage/page/cache.ts`
**Changes**: `revalidatePage` encodes the page URL and sends the header.

**File**: `.../controller/singlepage/page/cache.spec.ts`
**Changes**: add the variable and header to the `@sps/shared-utils` mock and a scenario for the request `revalidatePage` sends.

#### 4. Boot report

**File**: `libs/shared/utils/src/lib/secret-strength/index.ts` and its spec
**Why**: an upgrade that misses the variable is reported at API start, like the other transported secrets.
**Changes**: add `HOST_SERVICE_REVALIDATION_SECRET` to `CHECKED_SECRET_NAMES` after the MCP exchange secret (reported, not fatal); update the ordered spec.

## Phase 3: Environment carriers and documentation

### Overview

Both services receive one value locally and in deployment, and operators know
what to do on upgrade.

### Changes Required:

#### 1. Local bootstrap

- `apps/api/create_env.sh`: generate the value with `generate_secret 32` beside the MCP exchange secret.
- `apps/host/create_env.sh`: copy it from `../api/.env` with `get_env` into `.env.local`.
- `create_env.sh`: run the API's script before the host's.

#### 2. Deployer

- `tools/deployer/.env.example`: placeholder with a comment under the host variables.
- `tools/deployer/api.sh`, `tools/deployer/host.sh`: read the value and pass it to the playbooks.

## Testing Strategy

### Unit Tests:

- Host route: every refusal path, the unconfigured warning, and the three caller shapes (tag, layout, page).
- Middleware: header and encoding, both payloads through `init()`, refused and failed calls.
- Agent page cache: the request `revalidatePage` sends.
- Boot report: the new name in order.

### Integration Tests:

- None added. The API's HTTP proof covers the middleware with a real server; the host route runs in its spec with a real `NextRequest`.

### Manual Testing Steps:

1. Start a stub host on a free port that records the path, query and whether the header is present and matches.
2. Start the API on 4315 with `HOST_SERVICE_URL` at the stub and a generated value.
3. Create and delete a throwaway entity with the operator header; confirm the stub saw encoded tags with a matching header; stop both.

## Performance Considerations

One header and one constant-time comparison per call; no measurable cost.

## Migration Notes

- Existing deployments: generate one value, set it in `tools/deployer/.env`
  and both GitHub secret sets, and redeploy the API and the host. Until then
  the host refuses revalidation and logs why, and the API boot report names
  the missing value.
- Existing checkouts: `create_env.sh` scripts do not rewrite existing files;
  add the same generated value to `apps/api/.env` and `apps/host/.env.local`.
- Projects with their own senders of this route add the header.
