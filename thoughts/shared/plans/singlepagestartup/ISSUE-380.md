# План SEO для страниц, блога и каталога

Статус: редакция 2 реализована и проверена; задача передана в Code Review. Рабочая ветка — `codex/studio-linear-workflow`.

## Что подтверждено

Исследование: [ISSUE-380](../../research/singlepagestartup/ISSUE-380.md).

- Яндекс Вебмастер показывает 129 дублей title и description — 91% страниц в отчёте.
- Главная и проверенная страница товара сейчас отдают одинаковый title «М2коммерц» и description «Центр доходной недвижимости».
- Генератор SEO выбирает одну запись `primary` для всех адресов; связанные со страницей metadata и данные конкретной статьи или товара не используются.
- Canonical отсутствует; в поиске присутствуют рекламные варианты URL.
- Production sitemap пустой, его XML namespace некорректен.
- Проверенный несуществующий URL возвращает HTTP 200 с noindex. Вебмастер отдельно сообщает о неправильных 404.
- В общем компоненте rich text содержимое TipTap JSON появляется после клиентской инициализации. В коде также отсутствует html lang, а сохранённый alt изображения заменяется пустой строкой.

Данные сводки и диагностики Яндекса временно не обновляются; приведённые HTTP-наблюдения проверены отдельно 28.10.2026.

## Согласованные решения

Основа плана: существующая модель Host Metadata в БД, связь Page → Metadata, квадратные скобки для подстановок, вариант `hidden` для моделей и связей, отдельная связь Metadata → File. JSON-поле Article/Product/Profile и явные цепочки связей входят в согласованную редакцию 2.

### Метаданные и маски

Page выбирает запись Metadata через существующую `pages-to-metadata`. При нескольких связях используется первая доступная запись по `orderIndex`, затем ID связи; порядок виден в редакторе. `primary` задаёт общие значения сайта. Значения хранятся и редактируются в БД.

Серверная функция собирает результат из этих записей для Next.js. Исходный `actions/generate.ts` существовал до SEO-задачи; его проблема — чтение одной `primary` для всех URL. В согласованной реализации нужна одна операция разрешения метаданных и тонкий адаптер Next.js `generateMetadata`. Генерация текстов, запись вычисленных значений в БД и отдельный публичный action для этого не нужны. [Next.js Metadata](https://nextjs.org/docs/app/api-reference/functions/generate-metadata).

Основная запись маски — `[module.models.field]`, с теми же именами модулей и коллекций, что в URL. Для JSON-поля допускается дальнейший путь к свойству. Примеры будущего содержимого полей Metadata:

| Поле                          | Значение в БД                             | Источник                                                       |
| ----------------------------- | ----------------------------------------- | -------------------------------------------------------------- |
| title статьи                  | `[blog.articles.title] — М2коммерц`       | Статья, найденная по текущему URL; title на языке страницы     |
| description товара            | `[ecommerce.products.shortDescription]`   | Краткое описание текущего товара                               |
| title профиля                 | `[social.profiles.title] — М2коммерц`     | Профиль текущего маршрута                                      |
| keywords статьи               | `[blog.articles.metadata.seo.keywords]`   | Локализованный список в предлагаемом JSON-поле                 |
| title с отдельным SEO-текстом | `[ecommerce.products.metadata.seo.title]` | SEO-переопределение товара без изменения его видимого названия |

Для перехода по связи предлагается явная цепочка внутри тех же скобок: `[blog.articles>blog.articles-to-file-storage-module-files>file-storage.files.file]`. Она означает: текущая статья → её связи с файлами → поле `file` связанного File. Это расширение для метаданных; существующие URL-маски сохраняют свой контракт. Полные имена связей исключают догадки, к какой из сущностей относится файл или профиль.

Правила разрешения:

- Начальная сущность определяется точным параметром маршрута и SDK-запросом. Маска не запускает перебор всех записей и не выбирает случайную сущность того же типа. Для статической страницы доступны сама Page и явно связанные записи.
- Переходы выполняются через существующие связи и их внешние ключи. Разрешены только зарегистрированные публичные поля и связи; строка маски не является исполняемым выражением или произвольным API-адресом.
- Локализованные поля читаются на языке страницы. Для буквального текста на разных языках используются записи Metadata соответствующих локализованных Page. При отсутствии значения применяется содержательное значение той же локали; неподтверждённый перевод не подставляется.
- Строки вставляются как текст. Rich text преобразуется в обычный текст. Список keywords очищается от пустых значений и повторов; произвольный JSON не превращается в строку `[object Object]`.
- Связанные списки имеют определённый порядок: `orderIndex`, затем ID. Изображение — первый доступный подходящий файл; keywords — список строк. Неоднозначная множественная текстовая подстановка требует исправления маски в редакторе.
- Неверная маска показывается как ошибка проверки в редакторе. В публичном ответе нет сырых скобок и незавершённых фраз: применяется запасное значение всего поля, а ошибка сохраняется в диагностике. Сбой API остаётся серверной ошибкой.
- Приоритет title/description: заполненное поле выбранной Metadata с разрешённой маской → SEO-текст сущности → её обычное содержательное поле → поля Page → общие настройки. Значения `Page` и `Description` не используются как SEO-тексты. Для динамической страницы постоянный общий текст отмечается в проверке дублей.
- OG и Twitter используют тот же механизм. Пустые отдельные заголовки и описания наследуют рассчитанные title/description. Это не меняет H1 в контенте.

### JSON-поле и keywords

Рекомендация: добавить `metadata` типа JSONB сначала в Article, Product и Profile, с пустым объектом по умолчанию. Формат расширяемый, но известная секция `seo` проверяется схемой. Первые значения — `seo.title`, `seo.description` и `seo.keywords`; тексты локализованы, keywords содержат список строк по языкам. Остальные именованные секции допустимы в пределах ограничений размера и типов JSON. Маски получают доступ только к явно разрешённым публичным секциям.

У Message, Thread и Chunk поле `metadata` уже существует со своими назначениями. Их данные не перезаписываются общей SEO-структурой. Добавление поля во все модели сейчас затронуло бы 61 модель, включая служебные и финансовые; для текущего SEO это не требуется. Предлагаемый объём — три модели и общий формат, который остальные смогут принимать по мере необходимости.

| Что приобретаем                                                                             | Что потребуется учитывать                                                                   |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Отдельные SEO-тексты без изменения названия товара или статьи                               | Проверка локалей, типов и допустимых размеров                                               |
| Дополнительные подписи для карточек, признаки отображения, справочные сведения для экспорта | Владелец каждой секции, документация её смысла и совместимые изменения формата              |
| Новые необязательные свойства без отдельной SQL-колонки на каждое                           | JSON сложнее фильтровать, индексировать и согласованно обновлять                            |
| Использование одних данных в разных масках и представлениях                                 | Частичная правка не должна стирать соседние секции; нужны проверки конкурирующих обновлений |

Цены, права доступа, состояние публикации и ссылки на другие сущности сохраняют собственные поля и связи. Для файлов нужна настоящая связь с File. JSON не должен становиться второй системой хранения основных бизнес-данных или закрытых сведений, которые затем случайно попадут в HTML.

Keywords редактор задаёт у конкретной сущности, а Metadata получает их по маске. Буквальные keywords в Metadata статической страницы тоже являются редактируемыми данными в БД. Автоматический сбор всех слов текста, всех категорий или общего списка сайта не предусмотрен. Если значения отсутствуют, тег пропускается. При необходимости редактор может явно использовать маску конкретной связанной категории.

Google не использует `meta keywords` для индексации и ранжирования. Яндекс указывает, что тег может влиять на соответствие запросам. Поэтому поле поддерживается, но основные исправления относятся к содержанию, title/description, доступности и дублям. [Google](https://developers.google.com/search/docs/crawling-indexing/special-tags), [Яндекс](https://yandex.ru/support/webmaster/ru/controlling-robot/metatags).

### Author и viewport

`author` — имя реального автора материала. Для статьи допустим человек или редакция, если они действительно указаны авторами. Поле Metadata.author может содержать текст или маску. Существующая связь Profile → Article допускает несколько профилей и сама по себе не означает авторство: её нельзя автоматически трактовать как список авторов. Имя продавца, владелец сайта и текущий администратор тоже не становятся авторами автоматически. Если автора нет, тег пропускается. Для JSON-LD нужны подтверждённые имя и тип Person/Organization; имя без этих сведений можно оставить только в HTML metadata. [Автор статьи](https://developers.google.com/search/docs/appearance/structured-data/article#author-bp).

`viewport` задаёт отображение страницы на мобильном экране. Рекомендуемое общее значение — `width=device-width, initial-scale=1`; пользовательское масштабирование сохраняется. Это настройка Host, общая для товаров и статей. Next.js уже имеет подходящий default; отдельный запрос БД ради viewport не нужен. Существующее поле БД сохраняется для совместимости, помечается в редакторе как устаревшее и не создаёт второй тег. При переносе проверяются непустые значения; нестандартные настройки учитываются отдельно до развёртывания. [Next.js viewport](https://nextjs.org/docs/app/api-reference/functions/generate-viewport).

### Обложки

В Metadata сейчас нет полей изображения. Добавить текстовые `opengraphImage` и `twitterImage` с поддержкой масок, а также связь `host/metadata-to-file-storage-module-files` по существующим правилам связей с File: `metadataId`, `fileStorageModuleFileId`, `variant`, `orderIndex` и стандартные служебные поля.

Порядок выбора: изображение из явного поля или маски → первый доступный файл изображения, связанный с этой Metadata → изображение общей Metadata `primary`. Twitter при отсутствии собственного значения использует рассчитанное OG-изображение. Если доступной обложки нет вообще, тег изображения пропускается и редактор показывает предупреждение. Favicon не считается автоматически подходящей обложкой.

Так у главной, статьи и страницы товара могут быть разные обложки без файловых URL в коде. Учитываются `hidden` у File и связи, MIME, размеры, alt и абсолютный публичный URL. Явно настроенная маска с отсутствующим необязательным файлом использует запасную обложку. Ошибка сервиса файлов не подменяется успешным чтением. Настройка метаданных сама по себе не добавляет видимый блок обложки в тело страницы.

### Индексация и HTTP

Публичные материалы индексируются. Скрытые страницы и сущности возвращают настоящий 404; служебные страницы, которые должны оставаться доступными, получают noindex. Для редактируемого исключения доступной Page предлагается отдельное поле Page `indexing` со значениями `auto` и `noindex`; `auto` сохраняет правила служебных маршрутов. `hidden` имеет приоритет над этой настройкой.

Canonical отражает содержание и язык страницы. Рекламные параметры исключаются; `segment`, `intent`, `offer`, фильтры и пагинация проверяются по реальной бизнес-логике. Разные страницы пагинации сохраняют собственный canonical. Hreflang добавляется только для существующих эквивалентных переводов.

Отсутствие или скрытие основной сущности определяется до отправки HTTP 200. Режим метаданных, кеш и проверка маршрута оцениваются вместе по времени ответа. Обязательный динамический рендеринг всех страниц не является исходным решением.

## Этап 1. Метаданные страницы и сущности — высокий приоритет

**Что сделать**

- Выбирать локализованную Page с учётом языка и включить язык в ключ lookup: одинаковая маска у двух языковых Page не должна возвращать первую случайную запись. При переносе проверить реальные значения Page.language; текущее значение по умолчанию не доказывает наличие перевода.
- Использовать общие с URL-масками правила имён и извлечения параметров. Не применять алгоритм перечисления всех URL для построения одного title.
- Читать модели и связи через SDK. Host может собирать данные нижних модулей; Blog/Ecommerce/Social не импортируют Host Metadata.
- Согласовать кеширование метаданных, контента и sitemap: изменения Page, Metadata, JSON сущности, связи, файла или variant должны обновлять зависимые результаты. Ключи включают локаль и применимый контекст доступа.
- Пересмотреть существующий незакоммиченный черновик по этому контракту. Его внутренние actions и прежние тесты не закрепляют архитектуру нового решения.

**Где**

- Host Metadata SDK и модель: `libs/modules/host/models/metadata`.
- Связь `libs/modules/host/relations/pages-to-metadata`.
- Входная страница `apps/host/app/[[...url]]/page.tsx`.
- Контентные модели Article/Product/Profile, их SDK и связи с файлами; существующие shared utils для чистого разбора масок.

**Результат проверки**

Автоматически: две статьи, два товара и профиль получают свои title/description; проверяются локали, цепочки связей, пустые поля, keywords, изображения, ошибочные маски и отсутствие повторных одинаковых чтений. Вручную: редактор меняет запись Metadata или данные сущности и видит обновлённый HTML без правки кода. Данные другой сущности или локали не подставляются.

## Этап 1а. `hidden` у моделей и связей

Добавить `hidden` ко всем моделям и связям, сохранив остальные варианты. Отдельный `draft` не вводится. По текущей инвентаризации SDK `hidden` отсутствует у всех 61 модели и у 9 из 94 связей; наличие строкового варианта у остальных связей ещё не подтверждает работу фильтрации.

| Что скрыто                                                           | Поведение публичной страницы                                                                                            |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Page или основная сущность URL — статья, товар, профиль              | HTTP 404, без содержимого сущности и её JSON-LD; URL отсутствует в sitemap                                              |
| Связь, необходимая для существования конкретного вложенного маршрута | Этот маршрут возвращает 404; независимые маршруты сущности сохраняются                                                  |
| Связь карточки, картинки, виджета или необязательного автора         | Связанный элемент исключается; остальная страница остаётся доступной                                                    |
| Metadata или Page → Metadata                                         | Скрытая запись не используется; применяются разрешённые запасные значения. Для скрытия самой страницы нужен Page.hidden |
| Отдельный элемент списка                                             | Он исключается до пагинации и подсчёта количества                                                                       |

Страница ошибки дополнительно получает noindex; основное требование — HTTP 404. Ответ 200 с noindex не считается выполнением этого требования. [HTTP-статусы](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes).

**Что и где изменить**

- Обновить SDK-списки вариантов всех моделей и связей, административные select-поля и шаблоны `tools/plugins/sps-generator-plugin`. В БД variant уже текстовый; одно добавление значения не требует SQL-миграции.
- Согласовать публичные server/client readers и frontend-dispatch: скрытая запись не рендерится даже при явной передаче `variant="default"`; административные варианты остаются доступны с нужными правами. Проверять данные записи и связи, а не только название вызванного компонента.
- Применять общий критерий видимости к публичным чтениям, спискам, счётчикам, проверке маршрута, маскам и sitemap. Не фильтровать административные и внутренние бизнес-операции без разбора. `hidden` не заменяет RBAC.
- При скрытии инвалидировать уже закешированные страницы, метаданные, списки и sitemap. Административный просмотр не должен попадать в публичный кеш.
- В админке при возврате из hidden редактор выбирает публичный вариант. Предыдущее значение единственного поля variant автоматически не восстанавливается; это ограничение выбранного способа хранения состояния.

**Проверка**

Автоматически: полное покрытие SDK-каталога значением hidden; скрытие модели и связи через публичные client/server пути; пагинация; отсутствие утечки через маску, OG и JSON-LD; переходы видимый → hidden → видимый с обновлением кеша. Вручную: скрытая статья и товар возвращают сырой HTTP 404, администратор продолжает их редактировать, скрытие одной картинки не ломает страницу.

## Этап 2. Дубли, sitemap и robots — высокий приоритет

**Что сделать**

- Формировать абсолютный canonical текущей локализованной страницы.
- Согласовать canonical, внутренние ссылки, завершающий слеш и перенаправления.
- Добавить Clean-param для подтверждённых параметров отслеживания; сохранить значимые параметры.
- Генерировать корректный sitemap с конечными публичными URL, XML-экранированием и устранением повторов.
- Исключать личные маски до перечисления сущностей; раскрывать публичные маршруты с правами анонимного посетителя.
- Исключать hidden Page, сущности и определяющие маршрут связи, а также Page с noindex. Использовать тот же критерий видимости, что при прямом открытии URL.
- При сбое источника возвращать 503, не публиковать пустой успешный sitemap.
- Предусмотреть ограничения размера sitemap и разбиение для больших каталогов. Не подставлять время генерации вместо реального lastmod.
- Согласовать noindex и robots так, чтобы поисковый робот мог прочитать noindex.

**Где**

- `apps/host/app/sitemap.xml/route.ts`, `apps/host/app/robots.txt/route.ts`.
- Host Page service и SDK: `libs/modules/host/models/page`.
- Существующие общие утилиты маршрутов и константы.

**Результат проверки**

Автоматически: sitemap разбирается XML-парсером, содержит публичные канонические страницы и не содержит hidden/noindex, личных адресов, рекламных дублей и перенаправлений. Ошибка API не маскируется кодом 200. Вручную: выборочная сверка URL карты с фактическими ответами сайта и анализатором Вебмастера.

## Этап 3. Настоящие 404 и серверный HTML — высокий приоритет

**Что сделать**

- Возвращать 404 для неизвестной страницы, slug и отсутствующего файла.
- Обрабатывать hidden основной сущности до начала потокового ответа; этот результат должен совпадать с правилами этапа 1а.
- Различать отсутствие записи и сбой API: ошибка инфраструктуры должна сохранять серверный статус ошибки.
- Выводить текст статьи и описания товара в исходном HTML, сохраняя семантику rich text и работу редактора.
- Передавать язык документа и сохранённые alt изображений.
- Проверить основной H1, структуру заголовков и обычные ссылки навигации/пагинации на реальных собранных страницах. Исправлять подтверждённые нарушения, не добавляя второй H1 поверх существующего блока.

**Где**

- Catch-all Page, RootLayout, middleware и настройки Next.js.
- Серверный reader Host Page.
- Общий TipTap renderer и компонент File.
- Затронутые Blog/Ecommerce варианты по результатам проверки.

**Результат проверки**

Автоматически: проверка сырых HTTP-ответов 404/5xx и серверного текста без JavaScript в dev и production-сборке. Вручную: текст, ссылки и заголовки статьи и товара, мобильный viewport, редактор rich text и отсутствие ошибок hydration. Отказ API не становится ложным 404.

## Этап 4. Структурированные данные — после основных исправлений

JSON-LD — машинное описание уже существующего материала в HTML. `Article` обозначает статью, `BlogPosting` — её разновидность для записи блога. Это не новый видимый блок и не новая модель в БД. Разметка помогает поисковику понять заголовок, изображение и авторство; расширенное оформление результата не гарантируется. Для записи блога используется один BlogPosting, без второго дублирующего Article. [Schema.org](https://schema.org/BlogPosting), [Google Article](https://developers.google.com/search/docs/appearance/structured-data/article).

**Что сделать**

- Добавить BlogPosting для записи блога; Article применять к другим материалам, действительно являющимся статьями. Product использовать для конкретного товара соответствующего типа.
- Использовать те же разрешённые данные и механизм масок. `headline` берётся из фактического заголовка статьи, `name` товара — из его названия; рекламный суффикс HTML title не меняет название сущности в JSON-LD.
- Изображение должно соответствовать материалу: общая обложка сайта, пригодная для OG, не становится автоматически изображением статьи или товара в JSON-LD. Автора добавлять только при подтверждённых данных; все указанные авторы должны соответствовать странице.
- Добавлять Offer только при наличии достоверных цены, валюты и условий товара; не создавать фиктивные рейтинги и отзывы.
- Не считать createdAt в базе датой публикации без подтверждённого контракта.
- BreadcrumbList добавлять при наличии соответствующей навигации на странице.
- Выводить JSON-LD безопасно на сервере и проверить его валидатором.

**Результат проверки**

Автоматически: валидный и безопасно сериализованный JSON-LD, отсутствие скрытых данных и выдуманных свойств. Вручную: соответствие видимому содержимому, Schema.org validator и Google Rich Results Test. Для каждого типа указано, какие требования расширенного результата выполнены, а какие зависят от данных проекта.

## Этап 5. Проверки и передача изменений

Матрица проверки: главная, статическая страница, две статьи, два товара, профиль, категория, вторая страница списка, рекламный URL, неизвестный slug, отсутствующий файл, служебный экран и реальные языковые версии. Дополнительно: hidden Page/сущность/связь/файл, доступная noindex-страница, пустой JSON, отсутствующий перевод, несколько файлов и Metadata, ошибка маски и изменение связанного объекта.

Для каждого применимого случая проверить HTTP-статус, title/description, canonical, robots, OG, JSON-LD, исходный текст, внутренние ссылки и присутствие в sitemap. Отдельно проверить задержку первого и повторного ответа, отказ API, кеширование и обновление после изменения метаданных.

- Автоматические проверки: поведенческие Jest-тесты, TypeScript, lint/format, зависимости модулей и размещение файлов.
- Браузер: корректная сборка без ошибок hydration и client/server boundary.
- Регрессии: админка, вход, личные страницы и редактор контента.
- Передача: отдельный SEO-коммит в текущей ветке и Code Review после согласования и проверки.
- Downstream: инструкция по переносу в m2commerce.ru, проверке домена, языка, SEO-полей и содержимого sitemap.
- Перенос данных: через API/SDK создать или связать Metadata для реальных Page, записать маски и обложки, проверить заполнение локалей. Новые поля сами по себе не исправят старые общие значения в production.
- Порядок выпуска: совместимые добавления схем → API/SDK → редактор и Host → заполнение данных → HTTP-проверка. Для отката сохраняются прежние значения Metadata и связей; новые JSON-поля и файлы не удаляются автоматически. После первого использования hidden откат публичной фильтрации не должен снова открыть скрытые материалы.
- После согласованного развёртывания: повторная проверка production и отправка важных страниц на переобход; оценка новых отчётов после обхода.

## Уточнения реализации

Host catch-all работает по запросу. В production-сборке ISR fallback возвращал
DYNAMIC_SERVER_USAGE при чтении request headers/session; явный динамический режим
устраняет 500 и позволяет проверять hidden до отправки HTML. Публичный API сохраняет
своё кеширование с поколениями данных. Измерения первого и повторного HTTP-ответа
приведены в process; возврат к ISR требует отдельной проверки 404 и сессий.

Основное содержимое товарной страницы выводится сервером независимо от сессии;
корзина и оформление заказа остаются в клиентских Subject-компонентах. Предпросмотр
несохранённых масок использует read-only Host endpoint через Metadata SDK.

Admin includeHidden требует POST-права на коллекцию или operator credential.
PATCH-only редактору это право необходимо назначить отдельно. Hreflang не выводится
без подтверждённых эквивалентных переводов. Это не препятствует отдельным локализованным
URL, canonical и sitemap.
