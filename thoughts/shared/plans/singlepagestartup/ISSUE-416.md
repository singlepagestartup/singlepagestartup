# План реализации #416. Доступ к серверным сервисам

Сервис получает свои исходящие связи и дочерние модели через `this.module`, а сервисы нижележащих модулей через `this.modules`. Если дочерний проект добавляет публичный метод в `Order/service/startup`, TypeScript выводит его аргументы и результат при вызове из Agent. Для добавления метода достаточно изменить класс Order.

## Завершение миграции существующих вызовов

Два исполнителя на `gpt-6.2-sol` с усилием `xhigh` переносят серверный код и тестовые подмены. Ведущий проверяет общий результат.

1. Обновить генератор и материализовать карты локальных зависимостей во всех моделях и связях. Для Order разрешить `this.module.product`. Из Product закрыть доступ к Order, из Order закрыть доступ к собственному модулю через `this.modules.ecommerce`. Сохранить точные startup-типы при переходе из контроллера, модели и вложенной операции. Второй запуск генератора должен оставить файлы прежними.
2. Перенести зависимости Billing и Ecommerce. Сохранить обе подмены в `createOrderBootstrap(reservations?, paymentIntent?)`. Subject использует оплату и резервы конкретного Order во всех ветках оформления заказа. В Knowledge сохранить общий контекст транзакции для пяти сервисов и индексацию после успешного коммита.
3. Перенести остальные модули, приложения и тесты. В RBAC Subject использовать `service.module.identity`, `service.modules.crm.form`, `service.modules.billing.currency`. Удалить устаревшие поля, интерфейсы, конструкторные параметры и DI-токены, включая одиночные дубли разрешённых сервисов. Сверить по исходникам специальные обработчики, права доступа и привязку к текущей сборке. Перенести инструкции для дочерних проектов.
4. Проверить типы, переход к определению, общий экземпляр при прямом и HTTP-вызове и независимость двух сборок. Выполнить линтер, тесты генератора, модульные и интеграционные наборы. На отдельной базе проверить оплату, повтор, позднее подтверждение, отмену, отказ доступа, Knowledge commit/rollback и сценарии 152, 154, 258 и 414.

В сборке модели контроллер уже получает экземпляр сервиса из своего контейнера. При обращении из другого модуля часть потребителей вызывает фабрику владельца, а часть создаёт сервис заново. Работы касаются серверных сервисов, их привязки к контроллерам, генератора и проверок зависимостей. Публичный HTTP API, пользовательский интерфейс, схема БД и данные лежат за пределами задачи. Действия от имени пользователя проходят через Permission и RBAC Subject. Порядок модулей и владение связями задаёт [контракт зависимостей](../../../../.agents/contracts/engineering/module-dependencies.md).

## Phase 1: Типы и экземпляры на пути Agent → Order

Расширить `createAppBootstrap` в `libs/shared/backend/api/src/lib/app/bootstrap.ts`. Каждая сборка API или теста принимает свой набор подмен. При первом обращении она вызывает фабрику владельца или берёт переданную подмену. Этот экземпляр получают и контроллер, и остальные потребители сборки. Общая библиотека управляет временем жизни объектов. Имена модулей, сущности и типы их конечных классов объявляют владельцы в существующих пакетах `backend/app/api`.

В Agent подключить `this.modules.ecommerce.order` к фабрике Order и убрать ручное перечисление его методов. Тип выводить из конечного класса, экспортированного из `service/startup`. Сохранить стандартные вызовы `createService()`, `bootstrap()` и подмену резервов и оплаты через `createOrderBootstrap`. До переноса остальных потребителей старый путь к Order должен возвращать экземпляр из той же сборки.

## Phase 2: Генерация разрешённого доступа

В существующих `Coder.ts` модуля, модели и связи дополнить создание и удаление сущностей. Все три находятся под `tools/plugins/sps-generator-plugin/src/coder/root/libs/modules/[module]`, в каталогах `backend/app/api`, `models/[model]/backend/app/api` и `relations/[relation]/backend/app/api`. Обновить соответствующие шаблоны bootstrap и сервиса. Генератор регистрирует фабрики сущностей в пакете владельца отдельно от списка HTTP-приложений в `apps.ts`.

Из утверждённого порядка модулей построить для каждого потребителя типизированный список всех моделей и связей ниже него. Новый модуль получает согласованное место в этом порядке. Внутри модуля разрешать зависимости по владению. Например, Topic может использовать TopicsToNotifications, а тип Notification исключает эту входящую связь. Проверять циклы в графе собираемых сервисов. Расширить проверку в `tools/agents/module-dependencies.mjs:176` на обращения через файлы реэкспортов своего модуля с учётом различий между зависимостями сервисов и ссылками схем на внешние ключи.
