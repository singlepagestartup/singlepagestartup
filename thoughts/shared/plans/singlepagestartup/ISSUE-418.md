# План внедрения #418. От обращения клиента до исполнения заказа

Менеджер описывает этапы воронки обычным текстом, назначает человека или ИИ и видит ход работы в канбане и таблице. ## 1. Архитектурные контракты и идентичность

- **CRM** владеет воронкой, черновиком и неизменяемой публикацией, этапами, задачей, событиями и связями с товаром, предложением и заказом. **Social** владеет связью треда с задачей, профилями и назначением эксперта товару или предложению. **Knowledge** хранит источники, версии и индекс.
- **RBAC** определяет инициатора из сессии, исполнителя, разрешённых плательщика и получателя, делегированные действия и права на файлы. Здесь же находятся настройки доступа к подключениям магазина и внутренние переводы Subject. **Agent** принимает события работы, сохраняет запуск и его попытки, вызывает нижние домены по их контрактам. **Host** компонует страницы через нижние виджеты. Внешний HTTP-вызов выполняет серверный адаптер.
- **Ecommerce** владеет заказом, котировкой и выдаваемой версией товара. **Billing** владеет денежным инвойсом и состоянием платежа. Каждый домен записывает факт и событие к отправке в одной транзакции. Верхний потребитель связывает их с задачей. Broadcast доставляет события с повторами. При обработке сервер проверяет сохранённый ключ выполненного действия. [Возможности Broadcast](../../../../libs/modules/broadcast/models/channel/README.md#L44)
- Задача хранит публикацию воронки, стабильный ID этапа, состояние исполнения, ожидаемое событие, исход, срок и ревизию. У событий есть ID причины, актор, время, доказательство и уникальный ключ операции. У запуска — ID задачи и события, ревизия назначения, статус попытки и ссылки на расходы. Транзакционная граница исключает переход без записи истории. У сетевого вызова своя попытка до отправки и фиксация результата после ответа.
- Один серверный переход используют менеджер и агент. Допустимые действия задаёт пересечение прав субъекта, назначения и перечня этапа. Агент выбирает из них по тексту. Сообщение, вывод JEV или ручное перемещение карточки могут подтвердить консультацию по правилам этапа. Проверку оплаты, выдачи доступа и факта доставки выполняют их домены.
- Пакеты регистрировать у владельцев. Применять `this.module` для собственного модуля, `this.modules` для нижних, дочернюю сборку для общей транзакции. Обработчики HTTP только связывают маршрут, middleware и сервис. Схему Drizzle генерирует владеющая модель или связь.

**Критерии приёмки**

- [ ] Автоматически — проверить граф импортов командой `npm run check:module-dependencies` и контракты перехода/ключа повтора на тестовых событиях.

## 3. Версии CRM, переходы и рабочее место менеджера

- В `libs/modules/crm` добавить модели и связи по правилам репозитория, SDK, пагинированную выборку задач, журнал и команды сохранения черновика, публикации и перехода. Опубликованные условия действующей задачи закреплены. Редактирование и изменение порядка создают новую публикацию для новых задач. Осознанный перенос открытой задачи требует сопоставления старого и нового этапа, прав и записи причины.
- Сервер сверяет магазин, доступ субъекта, ревизию, срок назначения и основание. Записывает историю и следующую дату действия. Во время ожидания модель не вызывается. Напоминание выполняется в срок с ключом задачи, этапа и номера напоминания. Ответ, смена этапа и передача исполнителя отменяют устаревшие таймеры. По истечении срока зафиксировать исход «выполнено» при достаточном наблюдаемом результате либо «закрыто без результата» с последним достигнутым этапом. Новая консультация после закрытия получает новую задачу.
- В `libs/modules/rbac` подключить рабочее место магазина через собственный Widget с проверкой доступа на сервере. Администратор попадает в него из CRM Admin V2, менеджер — со страницы своего магазина по праву на работу с его задачами. Существующая оболочка Admin V2 требует глобальной роли. Предоставить менеджеру локальный доступ. Host получает нужные ID в `Page variant="url-segment-values"`, Website Builder отвечает за представление, доменный виджет — за субъект, чтение и действия.
- Оба вида читают одну серверную выборку через SDK. Использовать общий React Query cache, штатное обновление после мутации и WebSocket для другого сеанса, стабильный ключ и обработчик строки, состояние ожидания по ID. Индексировать выборку по магазину, воронке, этапу и дате обновления. Историю и расходы загружать по открытию карточки. [Контракт frontend](../../../../.agents/contracts/engineering/frontend-components.md)

## 4. Вход из магазина, персональный исполнитель и память

| Событие                            | Записи и навигация                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| «Задать вопрос»                    | Определить магазин, товар и выбранное предложение из серверных связей. Выбрать опубликованную воронку консультации. Создать задачу, чат и один дефолтный тред, направить в тред. Каждый новый осознанный запрос получает свой ID. Повтор одного действия из-за сети возвращает прежний результат.                                                                                                                                                                                                     |
| Добавление товара или заказ услуги | Найти или создать разрешённый активный черновик, связать заказ и покупателя с задачей, обеспечить чат и дефолтный тред. Покупатель остаётся на месте. Оплата готового товара доступна сразу, услуги с приёмкой — после принятия результата. Создание записей не вызывает модель. Если консультация приводит к покупке, передать её явный ID и сохранить связь обсуждения с заказом.                                                                                                                   |
| Свободное сообщение или CRM-форма  | В известном активном треде продолжить его задачу. Новое обращение по привязанной форме создаёт задачу и уведомление. В свободном чате выбрать одну из применимых воронок. При неоднозначности запросить уточнение. Для платной классификации заранее определить инициирующий магазин и его бюджет.                                                                                                                                                                                                    |
| Изменение корзины                  | На удаление закрыть поручение по черновику с причиной, сохранить историю и тред. Повторное добавление создаёт новую работу. Отличать обычное повторное добавление SKU от двух независимых заказов одной услуги. Во втором случае ключом служат поручение и предложение. Передавать точные `orderIds`. Если активный инвойс уже объединяет несколько заказов, из карточки одного показать состав группы и отдельный переход к групповому checkout. Автоматически оплачивать соседние заказы запрещено. |

Назначать одного персонального Subject-ассистента по уникальной паре «клиент–магазин». Повторный вход и два одновременных действия возвращают того же исполнителя. У него собственный AI-профиль, кошелёк и чат каждой задачи. Гостю присвоить проверяемую гостевую сессию. При входе в аккаунт подтверждать принадлежность обеих сессий, блокировать объединяемые записи и сохранять историю. Совпадение контактных данных не даёт доступа к закрытому чату, памяти, переводу или оплаченному файлу. Платные поручения с личного баланса и запись постоянной памяти доступны после установления владельца. Учесть существующее объединение корзин. [Объединение гостевой корзины](../../../../libs/modules/rbac/models/subject/backend/app/api/src/lib/service/singlepage/ecommerce/order/merge-guest-cart.ts)

Эксперта настраивают через админку. Приоритет назначения в магазине — конкретное предложение, товар, ближайшая применимая категория. При равнозначных назначениях показать конфликт администратору, в работе запросить уточнение или передать менеджеру. В задаче о смартфоне использовать точную модификацию, паспорт и актуальные разрешённые источники её эксперта. Архивная характеристика купленной модели доступна по конкретному заказу. Источники аккумулятора строительной техники не участвуют в подборе.

Профессиональная методика и Social Skills живут у эксперта. Личная память — обычный Knowledge Source профиля клиента с областью магазина и, при необходимости, ID бренда/проекта. «Запомни для “Севера”, что мы обращаемся на “вы”» сохраняет запись в разрешённом проекте. В другой задаче того же клиента сервер читает текущую опубликованную экспертизу и разрешённую личную память. Личный ассистент сохраняет идентичность при смене товара. Общие документы и ключи не копируются. Сервер фиксирует ID и версии использованных источников для объяснения прежнего ответа.

Проверять область поиска до отбора фрагментов, прямое чтение, запись, вложения и каждый инструмент. Запрос клиента на запоминание не меняет документы эксперта. Отзыв доступа, исправление и удаление источника учитываются при следующем чтении, в кэше и сжатой истории. Треды разных задач не служат общим хранилищем памяти. Менеджер получает уведомление и читает только разрешённые ему данные. При смене исполнителя повысить ревизию назначения и остановить действия старого запуска. Доставленный ответ автора сохраняет его Subject.

**Критерии приёмки**

- [ ] Автоматически — два клиента, два магазина, два бренда, параллельный вход гостя, повтор события, устаревшая ревизия, попытки прочесть чужой источник по ID и через поиск.
- [ ] В браузере — покупка без захода в чат, новая консультация по тому же товару, удаление и повторное добавление без ошибки, возврат в историю. Повторить после выхода А и входа Б в том же браузере с прогретым кэшем. У старого и нового клиента появляется обновлённая характеристика смартфона. В стратегии «Севера» учитывается его обращение на «вы», у второго клиента оно отсутствует. После передачи отвечает назначенный менеджер.

## 5. Подключения провайдеров, бюджеты и переводы за работу

### 5.1. Два субъекта и исходящая Identity

**Личный ассистент** ведёт CRM-задачу, читает разрешённые знания и отвечает клиенту. **Агент магазина для OpenRouter** — отдельный RBAC Subject со своим кошельком. Он выполняет делегированную операцию, например «создай одно превью по этим требованиям». Для прямого OpenAI магазин может зарегистрировать второго такого агента. Сторонний провайдер получает запрос на внешнем API, его аккаунт принадлежит владельцу ключа. Один технический Subject можно назначить нескольким ассистентам своего магазина. Владелец может пополнить его внутренний кошелёк обычным переводом. Это пополнение имеет собственное основание и не пополняет внешний кабинет.

| Запись                                     | Что в ней хранится и кто управляет                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Subject исполнителя провайдерских операций | Магазин, владелец, роль с разрешёнными операциями, кошелёк SPS. В профиле по необходимости хранятся инструкция и знания для работы с провайдером. Для прямой отправки HTTP дополнительный вызов LLM не требуется.                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Исходящая RBAC Identity                    | Отдельная закрытая связь RBAC закрепляет исходящую Identity за одним техническим Subject магазина. В ней действуют уникальность владельца Identity и проверка назначения на создание и изменение. Новое назначение, например `outbound_api`, отличает её от Identity для входа в SPS. В ней указываются провайдер, безопасная метка, внешний аккаунт, версия и закрытая ссылка на секрет. Один Subject может иметь несколько Identity. В первом релизе один провайдерский аккаунт закреплён за техническим Subject, разные ключи этого аккаунта различаются по ID и версии. Для другого внешнего аккаунта создать отдельного Subject. |
| Назначение ассистенту                      | Владелец задаёт разрешённую связь «ассистент → Subject провайдерских операций», возможности, модели и Identity по умолчанию для каждой операции. Правило экспертного профиля действует в магазине, индивидуальная настройка ассистента имеет приоритет в тех же пределах. Сервер проверяет магазин, полномочия, состояние Identity и назначения при каждой попытке. Если подходящей связи нет, уведомляет владельца и ставит работу на паузу.                                                                                                                                                                                         |

Существующие Identity служат для входа и контактов. Сейчас обычный ответ API скрывает пароль, соль и код, operator-доступ и внутренний сервис видят полную строку. Штатная связь уникальна по `identityId`. В `authentication/me` наличие хотя бы одной такой связи выставляет признак `authenticated`. На эти связи также опираются объединение гостя и удаление последнего способа входа. Dump и seed модели выключены. Добавить отдельное серверное назначение и ссылки на версии секрета. У существующих строк исходное назначение сохраняется. Ограничить обе связи на запись, в том числе через общий и привилегированный CRUD, чтобы исходящую Identity нельзя было присоединить как способ входа. В общем чтении и фильтрации доступны только разрешённые метаданные. Проверить поиск входящих Identity по provider и идентификатору, включая обе выборки EVM. Для исходящих Identity закрыть вход, выпуск JWT, password reset, универсальную привязку к другому Subject и редактирование секретных реквизитов через обычный CRUD. Поля `password`, `salt`, `code`, `account` и `email` у исходящей Identity оставить пустыми. [Проверка authenticated](../../../../libs/modules/rbac/models/subject/backend/app/api/src/lib/service/singlepage/authentication/me.ts#L18) · [Выбор Identity для входа через EVM](../../../../libs/modules/rbac/models/subject/backend/app/api/src/lib/service/singlepage/authentication/ethereum-virtual-machine.ts#L72) · [Модель](../../../../libs/modules/rbac/models/identity/README.md) · [Схема ответа](../../../../libs/modules/rbac/models/identity/backend/repository/database/src/lib/index.ts#L13) · [Настройки экспорта и привилегированного чтения](../../../../libs/modules/rbac/models/identity/backend/app/api/src/lib/configuration.ts#L21) · [Уникальность связи](../../../../libs/modules/rbac/relations/subjects-to-identities/backend/repository/database/src/lib/constraints/singlepage.ts#L11)

Владелец вводит или меняет ключ через выделенную операцию по TLS. В закрытом серверном хранилище значение шифруется с аутентификацией и версионируемым ключом шифрования вне БД в секретах развёртывания. В Identity лежит только ссылка. Получать по этой ссылке действующий ключ может серверный адаптер после проверки контекста операции и только для заранее заданного endpoint провайдера. При ротации сохранять ID прежней версии в истории. Сверка ранее отправленной операции использует разрешённый доступ к тому же внешнему аккаунту. Отзыв блокирует новые отправки. После записи очистить поле формы. Журнал connect/rotate/revoke хранит инициатора, магазин, Subject, ID и версию Identity, действие и исход. Исключить сырое тело запроса до записи Action Logger. Значение, внутреннюю ссылку секрета и заголовок авторизации исключить из ответов любого CRUD, SDK чтения, журналов запросов, событий, экспорта, MCP, промптов и ошибок. Для сверки выписки использовать отдельное разрешение.

**Делегирование.** У основной задачи один ответственный. Личный ассистент запрашивает дочернее поручение. Сервер создаёт его в Agent с ID родительской задачи и запуска, обоими Subject, разрешённой операцией, Identity, версией назначения, сроком и максимальной суммой. На первом этапе разрешить один уровень делегирования, без циклов и самостоятельной передачи дальше. В поручение попадают только необходимые данные — например, требования к превью и доступ к выбранному входному файлу. Дочерний исполнитель не наследует JWT, личную память, историю чата, права редактировать корзину или полномочия плательщика. Он сохраняет результат и внешние расходы, затем возвращает родителю ID результата и квитанцию. Клиент продолжает разговор с личным ассистентом. В случае отказа провайдера из-за исчерпания его баланса уведомить владельца внешнего аккаунта и записать исход попытки. При отмене/смене назначения блокируются новые эффекты, а уже отправленный вызов доводится до сверки.

У каждого внешнего **платного вызова** есть запись, в том числе при вложенном обращении из инструмента. Записать магазин, задачу, этап, запуск, попытку, личного ассистента и дочернего исполнителя, владельца внешнего счёта, провайдера, Identity и версию подключения, модель, назначение вызова, время, идентификаторы запроса и ответа, оплачиваемые единицы, валюту, способ получения стоимости и версию пересчёта в токены SPS. Использовать денежные типы с фиксированной точностью. Отсутствующие значения остаются неизвестными до сверки. Владелец видит расходы по задаче, агенту, провайдеру и подключению, включая незавершённые попытки.

Для OpenRouter сохранять ID генерации и предъявленную аккаунту стоимость. При расхождении с собственной оценкой показывать обе суммы, для сверки использовать метаданные генерации. Для прямого OpenAI сохранять ID ответа и usage по доступным видам единиц. При отсутствии суммы за один запрос вычислить её по зафиксированному прейскуранту и пометить как расчётную. Для нескольких ключей одного кабинета хранить общий идентификатор внешнего аккаунта. Выписку за период импортировать однократно и сверять на уровне поддерживаемой детализации. Разницу за день вынести в отдельную запись сверки, без произвольного распределения по задачам. [OpenRouter Generation](https://openrouter.ai/docs/api/api-reference/generations/get-generation) · [OpenAI Costs](https://developers.openai.com/api/reference/resources/admin/subresources/organization/subresources/usage/methods/costs)

Пересчёт воспроизводится по записи попытки. Например, при курсе 0,001 USD за 1 SPS расход 0,030 USD соответствует 30 SPS. Это пример версии формулы магазина. При оплате в другой валюте сохранить источник, время и значение обменного курса. Число входных и выходных токенов модели, списанные USD и переведённые SPS показывать отдельными полями. При расхождении после сверки записать отдельную корректировку с основанием.

### 5.2. Что разрешаем потратить до вызова

Лимит задаёт **сколько разрешено потратить**. Для производства владелец задаёт потолок задачи/этапа в настройках воронки и ограничения подключения. Для платного чата клиент заранее принимает цену или формулу и верхний предел своих списаний. Сервер сохраняет условия и время принятия. Резерв — временно занятая часть доступного баланса плательщика. Нулевой баланс агента допускается при достаточном покрытии на кошельке спонсора. Новый лимит требует явного решения уполномоченного плательщика.

Перед вызовом сервер ограничивает модель, объём входа и выхода, число изображений/инструментальных шагов и сторонние платные опции, рассчитывает верхнюю стоимость попытки по разрешённым параметрам. Под блокировкой проверяет остаток бюджета и доступный баланс с учётом всех открытых резервов. Не помещается — уменьшить параметры в согласованных пределах или перейти в ожидание бюджета. Если верхнюю стоимость выбранной операции нельзя ограничить, автоматический вызов не отправляется. Параметр длины ответа ограничивает только соответствующую часть одного вызова. [OpenRouter parameters](https://openrouter.ai/docs/api_reference/parameters)

При оплате по факту оплачивается исполненный объём. Например, при потолке 100 SPS попытке достаточно зарезервировать 40. Если основание расчёта даёт 26 SPS, списываются 26, освобождаются 14 и на задачу остаются 74 при отсутствии других обязательств. Отказ до отправки освобождает резерв. Неизвестный результат после отправки оставляет резерв и попытку на сверке. Подтверждённая работа провайдера записывается и при последующем отказе клиента от покупки. При превышении согласованной суммы провайдерский расход фиксируется целиком, превышение принимает владелец ключа, дальнейшие вызовы приостанавливаются. Клиенту нельзя молча повысить потолок.

### 5.3. Квитанция перевода и внешний счёт

| Операция                        | Источник и получатель                                                                                 | Основание                                                                                                                                                                                                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Оплата выполненной работы       | Внутренний кошелёк собственника или согласившегося клиента → кошелёк назначенного агента              | Этап, подтверждённый объём или принятый результат по версии тарифа                                                                                                                                                                                           |
| Отнесение затрат на внешний API | Кошелёк личного ассистента → кошелёк Subject, выполнившего поручение через свой OpenRouter или OpenAI | Внутренний эквивалент зарегистрированного расхода по версии формулы. Получатель заработал внутренние токены за операцию. Внешнюю сумму в валюте провайдера отразить отдельно. Переводы с технического кошелька требуют прав владельца или явного полномочия. |
| Внешний расход                  | Сторонний сервис списывает деньги с провайдерского аккаунта владельца ключа                           | Ответ, проверка генерации или выписка. Привязка к внутренней операции позволяет проверить расчёт. Пополнение кабинета выполняет владелец, оно не создаёт выручку SPS.                                                                                        |
| Покупка результата              | Покупатель → продавец по инвойсу Ecommerce/Billing, например 500 ₽ за принятую обложку                | Подтверждённая оплата точного заказа. Если выбран расчёт во внутренних токенах, одна операция закрывает эту цену.                                                                                                                                            |

Пример при оплате работы по факту. Собственник разрешил до 40 SPS. Клиентскому ассистенту причитается 38 SPS за работу, из них 30 SPS — стоимость поручения агенту OpenRouter. Одной группой провести 38 SPS собственник → личный ассистент и 30 SPS личный ассистент → агент OpenRouter. Остатки меняются на −38, +8 и +30 SPS соответственно. Ранее внесённое собственником пополнение кошелька провайдерского агента показывать как финансирование. Если это целевой аванс за поручение, привязать квитанцию к поручению, зачесть покрытую часть и перевести лишь остаток. Неиспользованный аванс вернуть связанной операцией. Ни пополнение, ни полученные 30 SPS не подтверждают внешний платёж. Сумму в USD и внешний аккаунт показывать рядом, исключая повторный счёт этих 30 как дополнительного расхода собственника. Если роль плательщика назначена клиенту, первый перевод идёт с его кошелька в согласованных пределах. Внешний счёт по-прежнему выставлен владельцу ключа.

Для услуги за результат спонсором производства служит собственник. Перед вызовом резервировать у него себестоимость производства. После подтверждённого вызова покрыть её переводом через ассистента к дочернему исполнителю независимо от продажи. Вознаграждение за принятый результат наступает отдельно по тарифу. При отказе клиента освободить остаток резерва и сохранить уже понесённый расход. Если тариф клиента меньше себестоимости, разницу несёт собственник при заранее разрешённом бюджете. До запуска сервер проверяет покрытие обеих частей. При неизвестном внешнем исходе резерв попытки остаётся до сверки.

Каждый кошелёк определяется парой Subject и Currency. Для перевода хранить ID обоих кошельков, сумму в одной валюте, инициатора, плательщика, получателя, основание, ID задачи, ключ операции, время и квитанцию. В одной транзакции заблокировать все участвующие в операции логические кошельки в постоянном порядке, проверить доступную сумму, учесть резерв, записать равные дебет и кредит и уникальную квитанцию. Учесть существующий баланс, который может состоять из нескольких строк. Блокировать также создание первого кошелька. При совместно наступивших обязательствах провести оплату агенту и отнесение расхода одной группой проводок. Если услуга оплачивается клиентом только после приёмки, спонсор покрывает производство отдельно. Повтор с тем же ключом и реквизитами возвращает квитанцию, с другими реквизитами — конфликт. Возврат и исправление — отдельные связанные проводки. Поддержать сверку остатков, резервов и оборотов с входящими пополнениями и покупками.

В предложении магазина указаны версия тарифа, валюта, фиксированная цена либо формула «стоимость подтверждённого объёма × коэффициент», источник курса и правило округления. Воронка указывает плательщика и событие применения. Формула использует разрешённые поля, проверяемые единицы и ограниченные операции. Фиксировать исходные величины и округлять один раз при выставлении суммы в согласованной валюте. Итог по предложению предъявлять клиенту до подтверждения соответствующей платной операции.

## 6. Оплата заказа, физическая доставка и приватная выдача

- **Услуга с постоплатой.** Привязать предложение магазина к воронке изготовления. При заказе услуги создать черновик и уточнить требования в треде. Генерация за счёт магазина сохраняет приватный оригинал и отдельное превью. Для картинки подключить инструмент, поддерживающий генерацию и выдачу файла. Для стратегии e-маркетолога артефактом служит PDF. Версии имеют отдельные ID. Сообщение «принимаю вторую» и кнопка принятия вызывают одну операцию с проверкой автора, задачи, версии и согласованной цены. При неясности переспросить. До принятия сервер блокирует checkout услуги с этим тарифом. При выставлении инвойса закрепить за платёжной попыткой точные orderId, resultVersionId, цену и валюту. Позднее подтверждение этого инвойса выдаёт закреплённую версию, в том числе при одинаковой цене двух версий. При смене версии до оплаты закрыть прежний счёт только после подтверждения отмены либо явно сохранить его исходное назначение. На этом шаге у клиента есть возможность оплатить выбранный заказ. Посторонние позиции корзины не включаются. Отказ и истечение срока до покупки сохраняют выполненную работу и расходы магазина.
- **Подтверждение и доставка события.** При успешном платеже Ecommerce под блокировкой подтверждает конкретный Order и в той же транзакции сохраняет событие к отправке в Broadcast. Потребитель проверяет заказчика, заказ, инвойс, успешный Payment Intent, сумму, валюту и принятую версию. Однократно записывает переход и выдачу. Пробуждение агента допустимо для пояснения в чате. Сбой модели или закрытый чат не задерживает выдачу оплаченного файла. Восстановление находит оплаченные заказы без подтверждённого результата. После сбоя отправки уведомления повторить доставку уведомления с тем же ключом. [Проверки Proceed](../../../../libs/modules/rbac/models/subject/backend/app/api/src/lib/service/singlepage/ecommerce/order/proceed.ts#L894)

Для покупателя создать связь `Subject → Role → Permission` на конкретный контент оплаченного заказа и методы GET/HEAD. Разрешение выдаётся однократно на принятую версию. Из истории покупок и треда вести к обработчику с проверкой прав. Проверить исходный storage URL, выдачу через CDN, прямой ID и кэш авторизованного ответа. При переводе старых чеков сначала проверить владельца и приватную копию по размеру/хешу, затем переключить ссылки, закрыть прежний объект и очистить кэш. Неоднозначные привязки закрыть до ручной проверки владельца. [Ссылка в истории покупок](../../../../libs/modules/ecommerce/models/order/frontend/component/src/lib/singlepage/purchase-ai-chat/ClientComponent.tsx#L96) · [Публичный обработчик](../../../../apps/api/app.ts#L124)
- **Физический товар.** Та же задача переходит через принятие в работу, сборку, передачу доставке с трек-номером и вручение. Для каждого перехода указать допустимый источник — назначенный сотрудник, подтверждение перевозчика или запись платежа. Порядок этапов и напоминания задаёт воронка. | Менеджер берёт у агента физический заказ и двигает карточку из таблицы, другой менеджер смотрит доску.                     | Старый запуск теряет право действия, оба видят одну ревизию. Трек и вручение подтверждаются независимо от текста ответа. Перезапуск и повтор события не дублируют назначение, расход или выдачу.                                                                                                                                |

**Критерии приёмки**

- [ ] Автоматически — проходят сборки, интеграционные тесты и сценарии из таблицы на чистой и обновлённой БД.
- [ ] Вручную — руководитель сверяет сквозные истории в двух сессиях, суммы, закрытые файлы и восстановление. Разработку можно считать готовой к ревью после фиксации доказательств по каждому этапу.
