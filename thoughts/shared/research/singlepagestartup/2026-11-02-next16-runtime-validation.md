## Dev and memory

Hardware: 18 GiB RAM, macOS arm64. A temporary watchdog sampled the complete
launched process tree every two seconds. It would stop dev at 6144 MiB and the
build at 10240 MiB; neither limit was reached. These are observed RSS samples,
not allocator guarantees or a benchmark against the old release. API and browser
memory are separate from the Host rows.

| Run                                                                  | Observed peak RSS, MiB |
| -------------------------------------------------------------------- | ---------------------: |
| First cold Turbopack dev                                             |                 4147.9 |

| Final cold dev, including the fixed API and existing browser session |                 4064.1 |
| Webpack production build, including TypeScript                       |                 2448.6 |
| Production server                                                    |                  625.7 |

The first dev run used `NX_DAEMON=false NX_ISOLATE_PLUGINS=false`; the warm and
final dev runs used the ordinary `npm run host:dev` launcher. No additional Node
heap cap or native bundler cap was supplied to dev. A Ready message was followed
by real page compilation and visible Browser verification; cold compilation takes
longer than server startup. No OOM, Rust panic or memory-watchdog stop occurred.

`experimental.turbopackMemoryLimit` is removed in installed Next 16.4.3. The old
SPS numeric setting is retired, and the runtime README describes Next's automatic
memory eviction and the distinction between a Node heap limit and total RSS.
The root AGENTS.md remains canonical; `agentRules: false` prevents generated Host
agent instructions.

## Production and cache

Full build command:

```sh
NX_DAEMON=false NX_ISOLATE_PLUGINS=false NEXT_TELEMETRY_DISABLED=1 \
NODE_OPTIONS=--max-old-space-size=8192 SPS_HOST_BUILD_CPUS=1 \
SPS_HOST_WEBPACK_CACHE=false npm run host:build -- --skip-nx-cache
```

The existing Nx executor is retained. Its `webpack: true` option selects Webpack
on Next 16; dev keeps Turbopack. The successful build compiled in 78 seconds,
finished TypeScript in 97 seconds, generated all six static routes and completed
traces/optimization. The memory flags match the previously documented local
Webpack procedure; no type-check bypass is enabled. A full Docker image was not
built. `npm run host:start` served the built artifacts.

For `/ru/framework`, two ordinary reads returned HTTP 200 and `x-nextjs-cache: HIT`.
POSTing duplicate `/api/host/pages` tags returned one acknowledged tag; the next
read returned `MISS`. The single-tag GET also returned 200 and caused the next
read to return `MISS`. The handlers use `revalidateTag(tag, { expire: 0 })`.
Malformed batch tags returned 400, and an unsupported locale returned 404.
These checks verify cache expiration without changing a business record.

See [revalidateTag](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)
for immediate expiration versus stale-while-revalidate behavior.

## Hono compatibility found during full build

The initial full type check exposed inherited Hono 4.13.16 incompatibilities:
JWT verification requires an expected algorithm, and route parameters are
optional until checked. Existing real-token helper tests failed before the fix.
RBAC session/refresh verification now explicitly expects HS256, matching the
existing signer. An algorithm mismatch maps to a sanitized credential error;
unsupported-algorithm/runtime configuration faults retain their own handling.
Required route values are checked before service calls and provider dispatch.
