# Research: Prevent server API function objects from crossing shared Server/Client component boundaries

**Date**: 2026-09-18T02:22:41+03:00
**Researcher**: flakecode
**Git Commit**: 29370bcbf85b195fbd1c2422707141135184d6e0
**Branch**: worktree-issues-2026-09-18
**Repository**: singlepagestartup

## Research Question

Issue #224 reports an intermittent production React Server Component (RSC) serialization failure in `host_host` whose safe fingerprint is an object with exactly the nine methods produced by the shared server API factory (`findById`, `find`, `count`, `update`, `create`, `findOrCreate`, `delete`, `bulkCreate`, `bulkUpdate`). The issue attributes it to shared frontend dispatchers that keep both `clientApi` and `serverApi` on `props`, pick `Client` when `isServer` is falsy, and then render `<Comp {...props} api={api} />`.

This document records how the live codebase behaves today:

- how each shared dispatcher chooses `Server` versus `Client` and exactly which props reach the `Client` branch;
- where `"use client"` / `"use server"` directives sit in those component folders;
- how model and relation adapters and their SDK packages build `serverApi` and `clientApi`;
- what `isServer` is, where it is required, and where it is set to `false`;
- how `apps/host` renders the public page tree and the admin trees;
- whether admin-v1 (`admin/*`) dispatchers share the pattern;
- what tests exist for these shared components and how they run;
- which claims in the issue match live code.

## Summary

- All eight dispatchers named in the issue, plus `subject-default`, use the same body: `const Comp: any = props.isServer ? Server : Client; const api = props.isServer ? props.serverApi : props.clientApi;` and render `<Comp {...props} api={api} />` inside `ErrorBoundary` / `Suspense` / `Provider` (`libs/shared/frontend/components/src/lib/singlepage/find/index.tsx:25-33`, `.../default/index.tsx:26-34`, `.../subject-default/index.tsx:26-34`, `.../admin-v2/{card,select-input,sidebar-item}/index.tsx:24-32`, `.../admin-v2/{table-row,form}/index.tsx:34-42`, `.../admin-v2/table/index.tsx:32-41`). The issue's line ranges are all still accurate at this commit.
- The four admin-v1 dispatchers (`admin/form`, `admin/select-input`, `admin/table-row`, `admin/table`) carry the identical pattern (`.../admin/{form,select-input,table-row}/index.tsx:24-32`, `.../admin/table/index.tsx:28-37`). `admin-v2/panel` and `admin-v2/table-controller` also branch on `isServer` and spread `{...props}`, but their prop contract contains no `serverApi` / `clientApi` (`.../admin-v2/panel/index.tsx:12-17`, `.../admin-v2/table-controller/index.tsx:12-17`).
- The `Client` branch of every dispatcher is a `"use client"` module with `import "client-only"` (`find/client.tsx:1-2`, `default/client.tsx:1-2`, `admin-v2/*/client.tsx:1-2`); the `Server` branch is a `"use server"` module with `import "server-only"` (`find/server.tsx:1-2`, `default/server.tsx:1-2`, `admin-v2/*/server.tsx:1-2`). Whether `<Client {...props} />` is serialized at all depends on where the adapter is imported from: from a Server Component the props must serialize; from a `"use client"` ancestor the whole subtree is client-bundled and nothing crosses a boundary.
- Adapters spread the same set into every dispatcher: `Component` (module child), `Provider` (from a `"use client"` module), `clientApi` (an object created by `factory` inside a `"use client"` SDK module), `serverApi` (an object created by `factory` inside a plain server module, `libs/modules/blog/models/article/sdk/server/src/lib/singlepage/index.ts:14-19`), then `{...props}` (`libs/modules/blog/models/article/frontend/component/src/lib/singlepage/find/index.tsx:11-16`, `.../default/index.tsx:12-18`, `.../admin-v2/table/index.tsx:13-22`). 1,753 adapter `index.tsx` files across `libs/modules` pass `serverApi={serverApi}`, and every one of them targets a shared dispatcher.
- `isServer` has no default. `ISpsComponentBase.isServer` is a required `boolean` (`libs/shared/ui/adapter/src/lib/interfaces/components.ts:3-7`); the dispatchers branch on truthiness, so a missing value selects `Client`. `admin-v2/table`, `table-row`, and `table-controller` narrow the type to the literal `false` (`.../admin-v2/table/interface.ts:19`, `.../table-row/interface.ts:19`, `.../table-controller/interface.ts:14`), `admin-v2/form` uses a discriminated union that forces `isServer: false` whenever `onSubmit` is present (`.../admin-v2/form/interface.ts:10-26`), and `admin-v2/panel` makes it optional (`.../admin-v2/panel/interface.ts:10`).
- The host catch-all page starts every tree with `isServer={true}` (`apps/host/app/[[...url]]/page.tsx:57`, `:62`, `:74`, `:76`). The root layout renders one SPS component with `isServer={false}` from a Server Component (`apps/host/app/layout.tsx:42`), but that variant uses a per-model dispatcher whose props are `{ isServer, variant }` and carries no API objects (`libs/modules/rbac/models/subject/frontend/component/src/lib/singlepage/authentication/init-default/index.tsx:10-22`).
- In admin-v2, sidebar items and cards render in Server mode (`isServer={props.isServer}` threaded from `page.tsx:57`), while every module overview switches to Client mode inside a `"use client"` wrapper that imports the whole model component tree (`libs/modules/blog/frontend/component/src/lib/admin-v2/overview/article/admin-v2-table/ClientComponent.tsx:1`, `:19-31`); 61 of 61 such wrappers carry `"use client"`.
- 14 spec files exist under `libs/shared/frontend/components`; all target `./Component`, `./client`, `./server`, or `./ClientComponent`, none imports a dispatcher `index.tsx`, and none renders through a real RSC boundary. The library runs Jest with `jest.client-preset.js` (`testEnvironment: "node"`, ts-jest) and per-file `@jest-environment jsdom` docblocks; server loaders are tested by calling the async component as a function and rendering the returned element (`.../admin-v2/card/server.spec.tsx:22`, `:55-76`). No file in `apps`, `libs`, or `tools` references `react-server-dom*`, `renderToReadableStream`, or `renderToPipeableStream`.
- The root README already states the allowlist rule for `Component.tsx -> ClientComponent.tsx` and the `isServer={false}` rule inside `"use client"` files (`README.md:279-282`, `README.md:366-368`); `AI_GUIDE.md:63-70` repeats the client-only rule. Neither document covers the shared dispatcher `index.tsx` files, and `eslint.config.mjs` has no rule about prop spreading or boundary directives.

## Detailed Findings

### 1. The eight dispatchers named in the issue

Every file has the same shape. Using `find` as the reference:

- `libs/shared/frontend/components/src/lib/singlepage/find/index.tsx:14-23` declares the prop type as `IComponentProps<M, V> & { Provider; Skeleton?; Component?; clientApi: ReturnType<typeof clientFactory<M>>; serverApi: ReturnType<typeof serverFactory<M>> }`.
- `:25` `const Comp: any = props.isServer ? Server : Client;`
- `:26` `const api = props.isServer ? props.serverApi : props.clientApi;`
- `:29-37` renders `<ErrorBoundary><Suspense fallback={props.Skeleton ?? <Skeleton />}><Provider><Comp {...props} api={api} /></Provider></Suspense></ErrorBoundary>`.

The same three statements and the same JSX appear at:

### 4. What the Client branch receives, and what it does with it

The spread at each dispatcher forwards the full adapter prop object plus `api`. In Client mode `api` is `props.clientApi`; `props.serverApi` remains on the object because nothing removes it.

Inside the branches:

- `find/client.tsx:14` calls `props.api.find(props.apiProps)` (a React Query hook from the client factory), `:16-20` runs `props.set(data)` in an effect, `:26-28` calls the `props.children({ data })` render-prop. `find/server.tsx:13` awaits `props.api.find(props.apiProps)`, `:19-21` calls `props.children({ data })`. `find/interface.ts:7-8` types `set` as a `Dispatch` and `children` as a function.
- `default/client.tsx:23-26` calls `props.api.findById({ id: props.data.id, ...props.apiProps })`, `:28-31` builds `passProps = { ...props, data }` and deletes `Component`, `Skeleton`, and `api`, then `:37` renders `<Child {...passProps} data={data} />`. `default/server.tsx:25-28` and `:34-39` mirror this on the server. Neither deletes `serverApi`, `clientApi`, or `Provider` from `passProps`.
- `admin-v2/card/client.tsx:21-30` calls `props.api.count(...)` with a `Cache-Control: no-store` header and `:32` renders `<Child {...props} isServer={false} data={[]} count={count ?? 0} />`. `admin-v2/card/server.tsx:20-29` awaits `count` and `:31-43` renders `Child` with an explicit list (`module`, `variant`, `isServer`, `data`, `name`, `type`, `apiRoute`, `href`, `count`).
- `admin-v2/sidebar-item/client.tsx:22` renders `<Child {...props} isServer={false} data={[]} />`; `server.tsx:21-31` renders `Child` with an explicit list (`module`, `variant`, `isServer`, `data`, `name`, `type`, `isActive`).
- `admin-v2/table-row/client.tsx:29-32` calls `api.findById`, `:38` renders `<Child {...typedProps} isServer={false} data={data} />`; `server.tsx:27-30` awaits `findById`, `:36-45` renders `Child` with `module`, `variant`, `isServer`, `data`, `name`, `type`.
- `admin-v2/table/client.tsx:60` creates `deleteEntity = typedProps.api.delete()`, `:135-154` calls `api.count` and `api.find`, `:324` renders `<Child {...typedProps} isServer={false} data={data} />`; `server.tsx:42-55` awaits `api.find`, `:61-67` renders `Child` with `variant`, `isServer`, `data`.
- `admin-v2/form/client.tsx:24-37` calls `api.findById` when `data.id` exists and renders `<Child {...typedProps} isServer={false} data={...} />` (`:34`, `:37`); `server.tsx:22-43` renders `Child` with `variant`, `isServer`, `data`.
- `admin-v2/select-input/client.tsx:21` renders `<ChildComponent {...props} />` (its own `./Component`); `server.tsx:20` renders `<ChildComponent {...(props as any)} />`.

So the Server branches of the admin-v2 loaders already pass an explicit list to the child, while every Client branch re-spreads the incoming object.

## Architecture Documentation

- Layering: `apps/host` route -> module component `index.tsx` (variant map) -> variant adapter `index.tsx` (binds `Provider`, `clientApi`, `serverApi`, child `Component`) -> shared dispatcher `index.tsx` (mode selection, `ErrorBoundary`, `Suspense`, `Provider`) -> `client.tsx` (`"use client"`, hooks) or `server.tsx` (`"use server"`, async fetch) -> module `Component.tsx` / `ClientComponent.tsx` (UI).
- Mode selection is a single boolean threaded from the route. `apps/host` passes `isServer={true}` at every entry, and the value flips to `false` only inside files that are themselves `"use client"` (module overview wrappers, admin-v1 shells, RBAC subject client components) or inside callbacks invoked by `"use client"` code (`adminForm({ isServer: false })`).
- Two coding conventions coexist in the shared library: Server branches pass an explicit prop list to the module child, while dispatcher `index.tsx` files and Client branches spread the incoming object. The root README's allowlist rule (`README.md:280`) is written for `Component.tsx -> ClientComponent.tsx` inside a variant folder, not for the shared dispatcher wrappers.
- The client SDK objects are created inside `"use client"` modules (`sdk/client/src/lib/singlepage/index.ts:1`), while the server SDK objects are created in plain modules (`sdk/server/src/lib/singlepage/index.ts`). Both are attached to props by directive-less adapter files.
- Test coverage of the shared components targets leaf files (`Component`, `client`, `server`, `ClientComponent`) with a `react-dom/client` harness under Jest; nothing renders a dispatcher `index.tsx`, and nothing exercises Next.js / React Flight serialization.
