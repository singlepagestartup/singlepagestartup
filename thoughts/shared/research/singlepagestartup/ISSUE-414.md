# Исследование #414. Цены по SKU магазина, доставка и допуслуги для каждой позиции корзины

**Дата** — 17 ноября 2026. **Исследователь** — flakecode.

**Репозиторий** — singlepagestartup. **Ветка** — `codex/issue-414-store-offers-and-cart-services`. **Коммит** — `93b0637e3dc56a25df9e4bba29907f203ba2fdf7`.

## Research Question

Где сегодня хранится предложение магазина, как его цена попадает в карточку, корзину, счёт и историю? Можно ли по текущим данным различить продавца и исполнителя доставки, сохранить две строки одного товара с разными условиями и начислить разовую услугу только один раз?

## Summary

Магазин уже может завести несколько SKU одного Product и привязать к каждому собственные атрибуты. Когда покупатель добавляет товар, форма передаёт Product и Store. Сервер записывает товар и количество в строку, а магазин связывает со всем заказом. По сохранённой строке нельзя определить, какой SKU выбрал покупатель. Карточка, корзина и оформление читают цены Product разными путями.

У счёта есть сохранённая сумма, у строки заказа нет снимка расчёта. Список покупок снова запрашивает цены товаров. Поэтому он может показать другую сумму после правки каталога. Проверки повторного платёжного уведомления и выдачи роли уже существуют и прошли на локальной PostgreSQL.

### Строка корзины, выбор услуг и вход в аккаунт

- Создание под блокировкой Subject проверяет активные заказы `cart/new` по `productId`. Повторная попытка добавить тот же Product конфликтует даже при другом Store. ### Смена магазина у позиции корзины

**Уточнение к #414.** Покупатель может выбрать другого продавца для той же модели и комплектации прямо в строке. Это требование к будущей корзине. Сейчас магазин связан с заказом, а строка хранит Product и количество. У группы из двух строк замена общей связи магазина изменила бы смысл обеих покупок. Для сравнения нужен ID конкретной строки и два розничных предложения `stores-to-products`. Запись подрядчика `provider` в выборе продавцов не участвует.

Пока покупатель сравнивает варианты, в корзине действует прежний SKU. Сервер считает оба предложения для текущего количества, адреса, валюты и числа единиц со сборкой. У каждого магазина покупатель видит товар, доставку, сборку и полный итог. Если сборки нет, покупатель может явно выбрать покупку без неё. При недоступной доставке нужно выбрать доступный способ получения. При подтверждении сервер повторно проверяет цену и доступность. Изменившийся итог требует нового подтверждения. Только после согласия покупателя в этой строке сохраняются предложение магазина и выбранные услуги.

**Практика площадок.** Яндекс Маркет описывает сравнение продавцов на карточке и условия доставки товаров в корзине. Amazon показывает на карточке предложения одного товара с учётом цены и доставки. TCGplayer позволяет после наполнения корзины сравнить текущий набор продавцов с другими вариантами и отменить замену. Для #414 согласован выбор продавца вручную у одной позиции. ### Уточнение для планирования. Как SKU, услуги и тариф образуют строку корзины

**Связи.** Основная строка ссылается на розничное предложение магазина. Его связи `delivery` определяют доступные способы получения, `add-on` — дополнительные услуги, `fulfilled-by` — исполнителя. В боковой корзине покупатель видит продавца и выбирает условия у каждой основной позиции. Указание адреса, точки выдачи, координат, размеров и массы определяется входами выбранного способа. Наличие опубликованной связи открывает выбор, а правило предложения определяет, обязателен ли он для оформления. Цифровой SKU без связей оформляется без доставки. У цифрового SKU с платной электронной выдачей появляется её цена, а почтовый адрес не нужен. Вид товара может служить для описания и поиска.

**Формулы и атрибуты.** Каждый участвующий в расчёте Product явно объявляет формулу строковым атрибутом с версией. Для основной строки пример — `unit_price * quantity`, где цена принадлежит выбранному SKU. Для Product услуги курьера — `dispatch_fee + rate_per_km * distance_km`, для Product сборки — `assembly_rate * serviced_qty`. У денежной ставки один источник: сервер находит Attribute выбранного Store по английскому `AttributeKey.slug` из формулы и валюте заказа. В схеме это `stores-to-attributes → attribute ← attribute-keys-to-attributes` и связь значения с валютой Billing. При выборе другого продавца расчёт читает атрибуты этого продавца. Внешний исполнитель определяется отдельно через `fulfilled-by`. При отсутствии формулы, обязательного входа или однозначной ставки в выбранной валюте сервер возвращает «Невозможно рассчитать» с причиной и блокирует оформление этой конфигурации. Явный ноль — корректная цена. Выражения используют ограниченный набор арифметических операций и переменных с единицами измерения.

**Упаковка.** Для перевозимой единицы используются внешние габариты упаковки и вес брутто: `length_cm`, `width_cm`, `height_cm`, `weight_kg`. Для нескольких коробок у каждого места свой набор значений. При расчёте доставки эти данные берутся у упакованного товара в основной строке выбранного продавца. Тариф указывает нужные входы. Например, `dispatch_fee + rate_per_km * distance_km + rate_per_kg * total_weight_kg` учитывает расстояние и суммарный вес упаковок для количества в строке. Объёмный вес можно выразить формулой конкретного тарифа. Общий делитель для всех продавцов не задан. Пересчёт количества обновляет начисления по правилам каждого выбранного предложения, затем итог заказа и итоги в валютах.

**Маршрут.** Первое подключение — Geoapify Routing API. Контрольный автомобильный маршрут между открытыми координатами 59.9311, 30.3609 и 59.9437, 30.2795 в Петербурге вернул HTTP 200 и 5 706 метров. Расчёт принимает `distance_km` в километрах. Серверный адаптер отвечает за вызов провайдера, перевод единиц и обработку недоступного маршрута. Выбор адаптера и его ключ относятся к конфигурации установки. При смене провайдера меняется источник расстояния, выражения магазина сохраняются. Если входом служит текстовый адрес, геокодирование выполняется отдельно. Контрольный запрос проверил только маршрут по координатам. [Geoapify Routing API](https://www.geoapify.com/routing-api/).

**Модель заказа и платежа для согласования.** При добавлении каждого основного предложения Subject создаёт отдельный Ecommerce Order с одной валютой. Основной товар и выбранные услуги получают строки `orders-to-products` с общим `orderId`. Дочерняя строка ссылается на конкретную основную строку, хранит собственный SKU, исполнителя, объём услуги и правило повторения. Для двух адресов можно разделить покупку на два заказа того же товара. Общая валюта распространяется на товар и все его услуги. В валюте заказа покупателю доступны варианты с действующим тарифом. Сменить валюту всего заказа можно в пределах пересечения валют товара и уже выбранных услуг. Смена продавца меняет один комплект и его пересчитанные условия только после подтверждения.

При оформлении совместимые разовые заказы в одной валюте попадают в общий платёж. Разные валюты образуют отдельные Payment Intent и Invoice. Подписка сохраняет самостоятельный договор периодических списаний; первая поставка может включать разовые услуги, продление берёт только повторяемые начисления. При фиксации оплаты сохраняется разбивка каждого счёта по заказам и конкретным начислениям за период с суммой и валютой. Сумма разбивки равна сумме счёта, повторная обработка той же оплаты не добавляет начислений. При отдельных валютных счетах каждый заказ отражает состояние своего платежа. Один платёж не завершает ожидающее списание в другой валюте. В истории одна строка на Order с раскрываемым составом и ссылкой на Invoice; если счёт общий, в итоги заказов попадают их собственные доли. Если для старого счёта сохранился только общий итог, показать его один раз без выдуманной разбивки.

| Заказ | Состав                                         | Сумма заказа | Счёт при совместном разовом оформлении |
| ----- | ---------------------------------------------- | -----------: | -------------------------------------- |
| A     | Шкаф 5 000 ₽, доставка 1 000 ₽, сборка 2 000 ₽ |      8 000 ₽ | RUB-1                                  |
| B     | Стул 3 000 ₽, самовывоз 0 ₽                    |      3 000 ₽ | RUB-1                                  |
| C     | Пакет токенов                                  |       20 USD | USD-1                                  |

Счёт RUB-1 — 11 000 ₽, USD-1 — 20 USD. После оплаты только RUB-1 заказы A и B оплачены, C ожидает оплату. При открытии A видны три начисления на 8 000 ₽. Основа для группировки — [текущий checkout](../../../../libs/modules/rbac/models/subject/backend/app/api/src/lib/service/singlepage/ecommerce/order/checkout.ts#L631). Связь с родительской строкой и зафиксированная разбивка — проект #414.

**Повтор заказа по подписке.** Предлагается сохранять согласованные условия первой и следующей поставки. Действующий тип покупки `one_off` или `subscription` задаёт разовую покупку либо расписание основного предложения. Для выбранной связи достаточно различить «при каждой поставке» и «только при первой». У обычной разовой покупки поставка одна. Например, кофе и курьер повторяются каждые четыре недели, подарочная упаковка только при первой отправке. Услуга «сборка» может повторяться, если это прямо предусмотрено условиями конкретной покупки. Для токенов без услуг в оплате только пакет. Первый платёж и продление показывают собственные итоги; при изменении согласованной стоимости следующей доставки нужен новый выбор до списания. У Tasty Coffee заказы на физический товар повторяются, каждый оплачивается отдельно, а изменение условий доставки согласуется с покупателем. [Подписка Tasty Coffee](https://shop.tastycoffee.ru/subscription).

**Объединение при входе.** Автоматическое слияние гостевой корзины с корзиной аккаунта не требует подтверждения. Для совпадающего товара берётся последний сохранённый выбор покупателя целиком: SKU, количество, адрес, валюта, доставка и допуслуги. В качестве единицы сравнения предлагается набор строк одной модели и комплектации в каждой корзине: если последним выбором были две строки с разными адресами, переносятся обе. Сравнивать время последней правки покупателем этих условий, включая добавление услуги; пересчёт по изменившемуся тарифу и открытие корзины не выражают нового выбора. При равенстве сохранить выбор аккаунта. Остальные товары и уже выставленные счета сохраняются. Явное подтверждение относится к выбору другого магазина после просмотра сравнения, либо к изменившейся цене перед оплатой.

### Остаток предложения и пересечение валют

В `stores-to-products` есть SKU и ссылки на Store и Product. В `stores-to-products-to-attributes` есть идентификаторы предложения и Attribute. Ни одна из этих таблиц не содержит поля data или payload. Существующий Attribute.number хранится как PostgreSQL numeric, а Attribute.string — локализованный JSON. Для остатка достаточно ключа `stock_quantity` с `field=number`: связать отдельное значение Attribute с одним SKU, разрешить владельцу этого Store и администратору вводить неотрицательные целые. У строки заказа quantity обозначает число выбранных единиц, у SKU stock_quantity — складской остаток. В расчёте стоимости количество товара и обслуживаемых единиц остаются отдельными входами. [Предложение магазина](../../../../libs/modules/ecommerce/relations/stores-to-products/backend/repository/database/src/lib/schema.ts#L17) · [Связь с атрибутом](../../../../libs/modules/ecommerce/relations/stores-to-products-to-attributes/backend/repository/database/src/lib/schema.ts#L17) · [Поля Attribute](../../../../libs/modules/ecommerce/models/attribute/backend/repository/database/src/lib/fields/singlepage.ts#L9).

API различает отсутствие связи (без лимита), ноль (распродано) и ошибочную настройку. Пустое значение, отрицательное число, нецелое значение или две конкурирующие записи остатка блокируют продажу этого SKU до исправления. Число передаётся без округления и потери точности. Для обычного добавления максимум равен доступному остатку за вычетом того, что уже выбрано по этому SKU; для редактирования строки из расчёта вычитается количество только в других строках. Услуга с собственным ограниченным SKU учитывается по количеству выбранных единиц этой услуги. Отдельные валюты, заказы и адреса одного покупателя используют общий остаток SKU. При сравнении магазинов у нового продавца проверяется полное запрошенное количество до замены. Если после слияния, повторения заказа или уменьшения остатка выбор уже нельзя выполнить, корзина сохраняет запрошенное количество и показывает доступный максимум для исправления.

**Резерв при подготовке счёта.** Открытая корзина проверяет доступность без удержания товара. При подготовке счёта сервер под блокировкой ограниченных SKU в постоянном порядке проверяет весь комплект и резервирует его в транзакции до передачи платежа провайдеру. Доступно для продажи = складской остаток минус действующие резервы. Оплата переводит соответствующий резерв в продажу один раз, окончательная отмена или истечение счёта освобождает его один раз. Тайм-аут запроса при неизвестном состоянии платежа сам по себе не освобождает товар. Для позднего подтверждения после освобождения резерва нужна сверка оплаты и остатка до исполнения. Отдельно проверить частичную оплату валютных счетов: переход одного счёта затрагивает только его заказы и их резервы.

Для карточки товара API возвращает валюты розничного предложения. Для корзины запрос с выбранным способом получения и допуслугами возвращает валюты, в которых рассчитывается весь выбранный комплект. Невыбранная услуга с единственной валютой не сужает выбор валют товара. Для каждой выбранной валюты сервер возвращает только доступные способы и допуслуги. Изменения тарифа, доступности, SKU или количества обрабатываются одной серверной проверкой при просмотре и записи; клиент отображает расчёт и состояние выбора. Контрольные случаи — SKU с остатками 3 и 0, отсутствие лимита, две строки одного SKU, последняя единица у двух покупателей и курьер, доступный только в RUB для товара с ценами RUB/USD.

## Open Questions

- При уменьшении количества с двух шкафов до одного, если сборка была заказана на оба, какое новое количество услуг подтверждает покупатель? Как совмещать количества услуг при объединении двух эквивалентных строк?
- Проект предлагает считать процент от стоимости обслуживаемых единиц после скидки и округлять каждое начисление. Примеры в целых рублях не определяют, как распределить скидку между единицами и округлить дробный результат в каждой валюте.
- Как магазин задаёт зону доставки и срок действия расчёта для выбранного тарифа? Расстояние для действующего маршрута поставляет настраиваемый адаптер.
- Как показать старую оплаченную покупку, если сохранился только общий счёт на несколько заказов, а разбивки по строкам на момент оплаты нет? Существующие данные подтверждают общую сумму такого счёта.
