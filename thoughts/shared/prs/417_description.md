## Summary

Серверные сервисы SPS получают локальные дочерние модели и исходящие связи через `this.module`, а модели и связи других модулей ниже по дереву через `this.modules`. Внутри Ecommerce заказ обращается к товару через `this.module.product`. Публичный метод, добавленный в `Order/service/startup`, доступен в Agent с его параметрами и типом результата. Контроллер, Agent и RBAC Subject используют один экземпляр Order в пределах сборки.

Closes #416.

## Changes

- Фабрика сервиса, HTTP-приложение и контроллер получают одну сборку. Тест может передать готовый сервис или фабрику подмены. Прямой вызов работает до запуска HTTP. Параллельный запуск и повтор после ошибки сохраняют экземпляр сервиса.
- Генератор модуля, модели и связи обновляет реестры по порядку модулей и владению связями. В проекте охвачены 15 модулей, 61 модель и 100 связей. Проверка зависимостей учитывает реэкспорты, типы и синхронные циклы фабрик.
- Реестры импортируют фабрики именованными ES-импортами. При первом обращении сборка создаёт сервис, при повторном возвращает тот же экземпляр.
- В истории покупок каждый товар отображается перед своими услугами. История передаёт `orderLineId` из платежной связи, поэтому клиент различает две строки одного предложения. Для старого заказа с единственным товаром услуги также видны под ним.
- Agent читает доменные сервисы из реестра. Subject получает из Order специализированные оплату и резервы. Для обычных операций Billing предоставляет собственный PaymentIntent. Host Page и отзыв ролей RBAC используют настройки владельца и при прямом обращении, и через HTTP.
- В транзакции Knowledge пять участников работают с репозиториями текущей транзакции. Остальные сервисы сохраняют экземпляры родителя. Успешная запись запускает индексацию после коммита, откат отбрасывает очередь.
- `npm run lint` проверяет исходники из корня репозитория, включая Studio и инструменты, затем проверяет порядок зависимостей SPS. Редактор и CLI читают один конфиг. Форматирование выполняет Prettier при коммите. ESLint различает отдельный импорт типов и повтор одного и того же вида импорта.
- В Preview AI Chat 45 импортов иконок указывали на локальный JSON, отсутствовавший в Git. Теперь они используют тот же набор глифов из отслеживаемого файла дизайн-системы Workspace.
- Контроллер Telegram сохраняет контекст обработчика-функции и принимает объект middleware Grammy. MCP проверяет поля записей контентного реестра перед использованием. Сценарии API и тесты Host используют типы SDK и фактические данные ответов.
- Вложенные операции RBAC, которым передаётся Subject, видят его типизированный реестр. Например, внутри создания заказа доступны `service.modules.crm.form` и `service.modules.crm.request`. Порядок модулей определяет доступные зависимости.

## Notes

ESLint показывает шесть предупреждений `no-explicit-any` в Host. Страница 404 получает вариант из сохранённой записи. Генераторы email, изображений и Telegram выбирают обработчик по имени варианта. Для строгой типизации на этих границах нужна проверка данных конкретного шаблона.

Тест общей библиотеки `Query Builder | Order By` уже помечен `describe.skip` в исходной ветке. Для существующих тестов контроллеров с открытыми после завершения Redis-соединениями использован `--forceExit`. Применение изменения не требует миграции прикладных данных.

## Downstream migration

- Если собственный Agent startup явно вызывает конструктор родителя, использовать `super(repository, telegramConversationRuntime)`. Зависимости домена доступны через `this.modules.<module>`. Перенести прежние вызовы `ecommerceModule.order` на `this.modules.ecommerce.order`.
- В собственных фабриках передавать текущую сборку владельцу сервиса. Для подготовленного экземпляра использовать `overrideService`, для экземпляра с зависимостями текущей сборки — `overrideServiceWith`. При подмене Order передавать в `createOrderBootstrap` согласованные сервисы оплаты и резервов. Заменить позиционные подмены старых групп Subject на подмены фабрик владельцев в сборке теста. В тестах Knowledge передавать File как `fileStorageFile`.
- При добавлении модуля указать согласованное место в порядке зависимостей и запустить генератор. Для Knowledge проверять и транзакционный File, и подмену сервиса родителя. Если `Offer.find` задаёт свою видимость предложений при проверке связей, передать соответствующий reader в `createOfferLinksBootstrap` и зарегистрировать эту фабрику для OffersToOffers в своей сборке.
- В собственном генераторе реестров импортировать каждую `createService` по имени и вызывать из геттера. Если тест подменяет весь модуль общей библиотеки API, сохранить экспорты, используемые при загрузке фабрик.
- Если проект собирает или отображает историю покупок своим кодом, передавать `orderLineId` из платежной связи и сопоставлять его с `parentLineId` услуги. Проверить заказ с двумя строками одного предложения.
- В проектах со своими целями Nx или настройками редактора перенести локальные правила в корневой конфиг ESLint и запустить `npm run lint` из чистой рабочей копии. Для собственных Preview проверить, что Git отслеживает все используемые файлы глифов.
- В расширениях MCP использовать тип модели для известных полей и проверять типы значений из открытого реестра. В HTTP-сценариях указывать ожидаемый тип ответа перед чтением полей.
- Если собственный тест корзины создаёт товар и магазин отдельно, создать также предложение в этом магазине, привязать цену и задать формулу товара с её версией. Проверить расчёт цены и повторное добавление товара через API.
- Если собственная операция получает Subject с типом `Pick`, использовать `SubjectServiceDependencies` для доступа к `service.module` и `service.modules`. Передать операции сервис из её тестовой сборки. Контроллер получает те же зависимости через `this.service`.
- В дочернем проекте проверить вызов собственного startup-метода из Agent, общую ссылку у контроллера, повтор оплаты и откат Knowledge.
