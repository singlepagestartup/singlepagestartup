Closes #311.

## Summary

RBAC subject tokens could not be told apart and could not be revoked. Every token was `{ exp, iat, subject }`, three of the five session sites embedded the whole subject row, the refresh route renewed any token that verified (including the access tokens the framework hands to Telegram, the agent module and the MCP exchange), a refresh token authorized requests, logout only deleted the cookie, and `me` answered the token's own claims.

Every token now names its type and its subject id alone, and each route accepts only the type it is for. Logout writes a per-subject revocation mark that every consumer of a token checks, and `me` reads the subject from the database. Sessions issued before the deploy keep working until they expire.

## Changes

- **Token format** (`@sps/backend-utils`): `signJwt` writes `exp`, `iat`, `jti`, `typ` (`access` or `refresh`) and `subject: { id }`. `verifyJwt(token, secret, { type })` refuses a token of the other type with 401 `Authentication error. Invalid token type`. A token without `typ` predates the change and is accepted as either type until it expires.
- **Issuance**: all thirteen sign calls go through `signJwt`: the pairs from `init`, email-and-password, `refresh`, the wallet login and the OAuth exchange, and the access tokens the subject controllers (audio transcription, OpenRouter reply, MCP server catalog), the agent module and the Telegram bot sign for their own calls.
- **Revocation mark**: nullable `tokensValidAfter` on the subject (migration `0005_green_celestials`, generated by `models:subject:repository-generate`). `isRbacSubjectTokenRevoked` in the subject SDK model refuses a token signed in or before the second of the mark.
- **Consumers**: the is-authorized service accepts access tokens and reads the mark through the subject repository, with a 30-second per-subject cache and `invalidateSubjectRevocationCache`. `refresh` accepts refresh tokens. The new `me` service returns the stored row (`null` for a deleted subject) and is the one resolver `init` and logout use. OAuth start takes the link-flow source subject only from a live access token. Route billing resolves the subject it charges through the is-authorized service, since its route is also reachable directly.
- **Logout**: writes the mark for the subject of a valid access token, drops the service cache and names the subject in `RBAC_REVOKED_SUBJECT_CONTEXT_KEY`; the is-authorized middleware then answers none of that subject's tokens from its decision cache. The response stays `{ data: { ok: true } }`. A missing, invalid, refresh or already revoked token revokes nothing.
- **Logout server SDK**: the subject server SDK logout action merges the caller's headers with the no-store header, as `me` does. It used to replace them, so a caller's `Authorization` header never reached the API, and a logout that depended on it (server-side callers, and browsers that send no API-origin cookie) revoked nothing while answering `{ ok: true }`.
- **One verifier**: in `libs/`, every presented subject token goes through `verifyJwt`. The twelve inline owner checks (ecommerce orders, identities, CRM request) and the ownership middleware `request-subject-is-owner` pass `type: "access"`; the actions logger, which only attributes an action, passes no type. Six authentication controllers call `jwt.verify` only to read `exp` from the pair the same request has just signed.
- **Errors**: `token revoked` is a 401 keyword in the HTTP error mapping.
- **Browser**: the response pipe clears a session refused as revoked even when a refresh token is stored, so another device of the subject starts an anonymous session instead of failing until its access token expires.
- **Docs**: subject README (Session Tokens, the new field, route descriptions), rbac README, the root README error table, and the subject OpenAPI paths for `me`, `logout` and `refresh`.

## Notes

- Logout ends every session of the subject, on every device. The module has no session model, and a per-device logout needs one. An MCP connector that stored the subject's access token has to be authorized again; the Telegram bot and the agent module sign a new token for every call.
- `iat` has one-second resolution, so a token signed later in the same second as the logout is refused too.
- The API process that handles the logout refuses the subject's tokens at once; another API instance does so when its 30-second cache entries expire.
- The transition branch for untyped tokens can be removed once the longest configured refresh lifetime has passed after the deploy (28 days with the defaults).
- `jti` makes every token unique and is not consulted yet; refresh-token rotation and `iss`/`aud` claims are not part of this change.
- The local run applied the subject migration to the shared development database.

## Downstream migration

Adaptation is required in every project on this framework: subject tokens carry a type and pass a revocation check, logout ends every session of the subject, and subject tokens signed by project code keep working only under the untyped-token transition.

**Applies to:** projects that sign or verify subject tokens in their own code, read subject fields other than the id from a decoded token, override the subject logout, init, me, is-authorized or billing-route services, construct those services by hand, call the logout server SDK from their own code, or run more than one API instance.

**Actions:**

- Run the repository migrations before the new API serves requests, so `sps_rc_subject` has the `tokens_valid_after` column.
- Replace project calls to `jwt.sign` for subject tokens with `signJwt` from `@sps/backend-utils` (type `"access"` for tokens sent to the API), and verify presented subject tokens with `verifyJwt` instead of `jwt.verify`, passing `type: "access"` where the token authorizes an action.
- Where project specs mock `@sps/backend-utils` partially for the owner-check controllers, the ownership middleware or the actions logger, add `verifyJwt` to the mock, for example `jest.requireActual("@sps/backend-utils").verifyJwt`.
- Read subject fields other than the id from the `me` response or the subject SDK instead of a decoded token, which now carries `subject.id` alone.
- Adapt startup overrides and hand-built instances of the subject services: logout takes `{ token }` and resolves to `{ subject }`, init takes a `me` resolver instead of `findById`, the is-authorized service takes the subject repository as a fourth constructor argument, and the billing-route service takes the is-authorized service as a third and resolves the charged subject through its `getSubjectId`.
- Pass the subject's access token as `options.headers.Authorization` where project code calls the logout server SDK: the action now forwards the caller's headers, and without a valid access token logout revokes nothing.

**Verify:** initialize a session, read a protected route with the access token (200) and the refresh token (401), refresh with the access token (401) and the refresh token (201), log out, and confirm every earlier token of that subject answers 401 while `init` starts a new subject; call `POST /api/rbac/subjects/authentication/bill-route` directly for a billable route with a refresh token and with a logged-out access token, and expect 401 for both; read an owner-checked route such as the subject's order list with the subject's refresh token and expect 401.
