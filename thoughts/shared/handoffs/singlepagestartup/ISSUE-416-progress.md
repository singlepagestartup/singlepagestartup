## Переход с групп сервисов на `module` и `modules`

Итоговая проверка охватила 161 серверный сервис, 96 локальных карт и 206 разрешённых локальных зависимостей. После повторной генерации исходники не изменились. TypeScript проверил API и Host, а Language Service подтвердил переход в startup из контроллера, сервиса Order и вложенной операции Subject. Проверка графа зависимостей нашла 0 нарушений в 16 179 файлах. ESLint завершился без ошибок, с шестью прежними предупреждениями Host.

Модульные тесты прошли в 23 из 23 проектов Nx. В рабочей копии выполнены 3 192 проверки, включая одну отдельную локальную проверку frontend SDK. Для версии клиентского SDK из PR отдельно прошли все 66 тестов. На изолированных PostgreSQL и Redis прошли 264 интеграционных теста в 16 проектах и 12 HTTP-проверок сценариев 152, 154, 258 и 414. Компиляция 280 серверных тестовых файлов отдельно от штатных TypeScript-проектов дала 54 ранее существовавшие диагностики против 269 до миграции. Новых диагностик нет.

## Проверка по исходникам

- Переход из Agent к добавленному методу находит его объявление в Order startup. Изменение только сигнатуры Order вызывает ошибку непосредственно в Agent. Обе операции прошли в отдельном окне VS Code на временной копии исходников. Дополнительно их воспроизвёл TypeScript Language Service.
- Для Notification исходные файлы Topic открывают TopicsToNotifications, а Notification получает свою исходящую связь с Template. Внешний список Broadcast пуст. Каждый геттер ведёт к bootstrap сущности и вызывает `createService(assembly)`.
- Telegram Agent подписывает токен покупателя и передаёт его в Subject SDK. API проверяет разрешение перед монтированным маршрутом. Subject сверяет пару subject/order и принадлежность каждой строки. Order предоставляет специализированные оплату и резерв для заказа.
- В Knowledge очередь индексации принадлежит операции записи. Цикл вызова обработчиков начинается после успешного выхода из транзакции. При исключении управление не доходит до этого цикла.

## Incident Log

<!-- incident-count: 14 -->

### Incident 1 — Подмена Order из другой сборки

- **Occurrences**: 1
- **Stage**: Phase 1
- **Symptom**: Две сборки в первой версии теста переиспользовали уже собранные экземпляры Order. Так сервис сохранял зависимости исходной сборки или получал вторую привязку.
- **Root Cause**: Готовый объект уже принадлежал другой сборке.
- **Fix**: `overrideServiceWith` передаёт фабрике целевую сборку и запоминает результат первого обращения. Готовый новый объект можно передать через `overrideService`.
- **Reusable Pattern**: Проверять фактический экземпляр у контроллера и потребителя в двух одновременно работающих сборках.

### Incident 2 — Тип дочернего HTTP-приложения затронул все 161 сущность

- **Occurrences**: 1
- **Stage**: Phase 3
- **Symptom**: TypeScript отклонил регистрацию каждого дочернего приложения из-за типа аргумента метода создания записи.
- **Root Cause**: Для монтирования маршрутов обёртка требовала весь интерфейс контроллера, включая операции над конкретной моделью.
- **Fix**: Ограничить интерфейс операциями монтирования и описания маршрутов, seed и dump. После исправления этой ошибки, типов дат отзыва и экспорта привязки сборки проверка `apps/api/tsconfig.json` прошла.
- **Reusable Pattern**: Тип регистрации приложения должен отражать операции владельца маршрутов. Компилировать реальный API со всеми сущностями.

### Incident 3 — Цикл Ecommerce при сборке каталога и связей предложений

- **Occurrences**: 1
- **Stage**: Phase 4
- **Symptom**: Анализатор обнаружил взаимное получение StoresToProducts и OffersToOffers.
- **Root Cause**: Каталог использует связи предложений, а проверка записи связи запрашивала сам каталог.
- **Fix**: Каталог получает связи из своей сборки. Запись связи читает сохранённые предложения через репозиторий под действующей блокировкой. Для собственной видимости предложений доступен типизированный reader.
- **Reusable Pattern**: Проверять обе точки входа и два направления ссылки с настоящими фабриками.

### Incident 4 — Транзакция Knowledge теряла подмену родителя

- **Occurrences**: 1
- **Stage**: Phase 3
- **Symptom**: Явно собранный Chunk получал File из стандартной сборки, а внутри транзакции терял стороннюю подмену Notification.
- **Root Cause**: Самостоятельная сборка транзакции знала только о пяти участниках, а явный граф не связывал их с общим владельцем.
- **Fix**: Привязать участники явного графа к его сборке. Дочерняя сборка транзакции заменяет пять участников и делегирует остальные владельцу.
- **Reusable Pattern**: Сравнивать ссылки на участника транзакции и отдельный сервис родителя.

### Incident 5 — Пропущенные ленивые вызовы фабрик

- **Occurrences**: 1
- **Stage**: Phase 2
- **Symptom**: Первый анализатор циклов пропускал обращение к владельцу через переменную с require.
- **Root Cause**: Проверка искала привязку только в статическом импорте.
- **Fix**: Учитывать синхронный вызов фабрики через require и её локальное имя. Импорт в асинхронной команде проверяется на направление и владение.
- **Reusable Pattern**: Проверять цикл сборки, отложенную команду и одноимённое связывание в другой функции.

### Incident 6 — В тестовом проекте генератора отсутствовал порядок модулей

- **Occurrences**: 1
- **Stage**: Phase 2
- **Symptom**: Тесты генератора останавливались при проверке позиции модуля.
- **Root Cause**: Старые фикстуры виртуального дерева не содержали утверждённого списка модулей.
- **Fix**: Добавить список в тестовые деревья и проверить создание, повтор и удаление с тем же контрактом, что в проекте.
- **Reusable Pattern**: Выполнять генератор на виртуальном дереве с его обязательными входами.

### Incident 7 — Тест зачисления пропускал чтение предложения

- **Occurrences**: 1
- **Stage**: Phase 4
- **Symptom**: Вместо ожидаемой ошибки зачисления тест получал ошибку чтения find у undefined.
- **Root Cause**: Ручная сборка в исходном тесте передавала только Order. Операция проверяет также StoresToProducts.
- **Fix**: Передать запрос предложений, который возвращает пустой список для синтетического заказа. На PostgreSQL повтор операции зачисляет сумму один раз.
- **Reusable Pattern**: Воспроизводить ветвь ошибки с действительными зависимостями операции.

### Incident 8 — Jest ожидал соединения Redis после завершения проверок

- **Occurrences**: 1
- **Stage**: Phase 4
- **Symptom**: Отдельные прогоны RBAC и Social выводили итог всех проверок и продолжали ждать.
- **Root Cause**: Существующие тесты контроллеров создают Redis-клиенты. Открытые соединения остались после всех утверждений.
- **Fix**: Сверить результат Jest и локальные сокеты. Для полных наборов использовать --runInBand и --forceExit.
- **Reusable Pattern**: Отличать ошибку утверждения от открытого ресурса после завершения теста.

### Incident 9 — Тест доставки Consistency на повторно использованной базе

- **Occurrences**: 1
- **Stage**: Phase 4
- **Symptom**: Общий интеграционный прогон завершился до доставки двух проверяемых событий. После него в outbox тестовой копии оставалось 1940 необработанных записей.
- **Root Cause**: Тест за ограниченное число итераций читает очередь, общую для всех проверок на этой копии базы. Предыдущие прогоны оставили в ней события.
- **Fix**: Штатный ConsistencyStore.dispatch обработал очередь на проверочной базе до нуля. Отдельный тест подтвердил доставку для обоих порядков коммита.
- **Reusable Pattern**: Проверять backlog тестовой базы перед повторным запуском интеграционного теста Consistency.

### Incident 10 — ESLint отклонил импорты в реестрах

- **Occurrences**: 1
- **Stage**: Code Review
- **Symptom**: В реестре Social ESLint выдал 30 ошибок `@typescript-eslint/no-require-imports`.
- **Root Cause**: Генератор загружал фабрики через `require()` в геттерах. Аннотация `typeof import(...)` проверяла тип и не меняла способ загрузки.
- **Fix**: Генератор создаёт именованные импорты. Геттер вызывает фабрику с текущей сборкой. В тесте Identity репозиторий подменяет только операцию записи, поэтому остальные экспорты доступны при загрузке.
- **Reusable Pattern**: Проверять сгенерированные файлы линтером и отдельно загружать реестры в Bun до запуска HTTP.

### Incident 11 — Услуга отображалась выше купленного товара

- **Occurrences**: 1
- **Stage**: Code Review
- **Symptom**: В одном из оплаченных заказов сборка стула стояла перед самим стулом.
- **Root Cause**: История покупок отбрасывала `orderLineId` при чтении платежных связей. Компонент показывал строки в порядке их получения.
- **Fix**: История возвращает ID строки заказа. Компонент показывает каждый товар вместе с услугами, чей `parentLineId` ссылается на эту строку.
- **Reusable Pattern**: Проверять порядок на перемешанных строках и на двух строках одного предложения.

### Incident 12 — В операции создания заказа редактор скрывал CRM

- **Occurrences**: 1
- **Stage**: Code Review
- **Symptom**: В контроллере Subject редактор предлагал `service.modules.crm`, а в `ecommerce/order/create.ts` выдавал TS2339 при обращении к `service.modules`.
- **Root Cause**: Subject передавал операции себя целиком. Тип параметра перечислял пять свойств и пропускал `modules`.
- **Fix**: Общий тип зависимостей операций Subject включает обязательный реестр текущей сборки. Операция выбирает из Subject только дополнительные свойства, которые использует.
- **Reusable Pattern**: Проверять подсказки и методы startup на типе, который получает вложенная операция.

### Incident 13 — Интеграционные фикстуры оплаты и CRM

- **Occurrences**: 1
- **Stage**: Implement, перенос потребителей
- **Symptom**: Тест CRM записал обычный Request и пропустил ожидаемое исключение после вставки связи. В Billing семь тестов дошли до ссылки на удалённый импорт.
- **Root Cause**: Некоторые фикстуры ещё передавали зависимости через старые конструкторы или создавали удалённую локальную переменную.
- **Fix**: Фикстуры CRM регистрируют обе подмены в сборке формы. Billing получает связь через фабрику в отдельной сборке. В PostgreSQL прошли обе проверки CRM и все 53 проверки расчётов Billing.
- **Reusable Pattern**: Проверять побочный эффект подмены, исключение и откат на реальной базе после переноса конструктора. Само создание объекта в JavaScript может пройти и с лишним аргументом.

### Incident 14 — Сборка операций RBAC при запуске API

- **Occurrences**: 1
- **Stage**: Implement, приёмка в Bun
- **Symptom**: API завершался при импорте SecurityNotifications с ошибкой Inversify о конструкторе без метаданных. После исправления загрузки запрос на изменение роли вернул HTTP 500.
- **Root Cause**: Два подкласса вручную собираемых операций ещё читали метаданные старых конструкторов. Фабрика отзыва роли передавала Order в устаревшем вложенном поле.
- **Fix**: Подклассы наследуют сигнатуру конструктора своих операций. Фабрика отзыва роли лениво передаёт типизированный Order. API стартовал, изменение роли тестового пользователя и сценарий повторной оплаты прошли.
- **Reusable Pattern**: После переноса DI проверить импорт всего приложения в Bun и выполнить бизнес-запрос через контроллер с настоящей сборкой.
